# AI 消费决策 Agent 开发记录

本文记录 AI 消费决策 Agent 开发中会影响架构、正确性、兼容性或演示可信度的问题。普通环境配置、一次性命令问题和明显的小错误不记录。

## 2026-08-14：现有数据不具备直接做评论 RAG 的条件

### 现象

原项目的 `tb_shop` 只有价格、坐标、评分和营业时间等结构化字段。`tb_blog` 仅有少量探店笔记，`tb_blog_comments` 没有种子数据，无法支撑“根据评论判断安静、排队、适合约会”等结论。

### 处理

新增 `ai_shop_profile` 存储菜系、场景、环境和排队风险等可维护画像；新增 `ai_review_document` 存储证据文本。演示数据使用 `SEED_DEMO` 来源标记，明确不是线上真实评论；已有探店笔记可使用 `BLOG` 来源。

### 影响

第一阶段可以完整演示“结构化召回 + 证据引用 + 重排”，但不能将演示数据表述为真实用户评论。后续接入真实评论或扩充公开可用数据后，再引入向量检索。

## 2026-08-14：JDK 21 与 MyBatis-Plus 3.4.3 的 Lambda 条件兼容性

### 现象

新增 AI 查询在运行期使用 Lambda 条件构造器时，MyBatis-Plus 3.4.3 尝试反射 `SerializedLambda`，在 JDK 21 模块限制下抛出 `InaccessibleObjectException`。编译可以通过，接口运行时才失败。

### 处理

AI 模块中避免使用 Lambda 条件构造器，改用显式列名的 `QueryWrapper`。这样不依赖旧版本 MyBatis-Plus 对 JDK 内部类型的反射。

### 影响

后续 AI 模块新增查询时，应继续使用显式列名条件；如果要全局恢复 Lambda 写法，需要先升级 MyBatis-Plus 并完成回归验证。

## 2026-08-14：模型复述会轻微篡改结构化事实

### 现象

DeepSeek 已成功调用，但最终回答把候选中的“运河上街店”复述为“运河上上街店”。候选数据本身正确，问题发生在自然语言生成阶段。

### 当前结论

模型适合生成取舍说明，不应拥有商户名称、价格、距离、营业时间等事实字段的最终表达权。

### 处理

最终答案改为由后端拼接商户名称、匹配依据和证据原文。模型只能输出不含店名、数字和事实字段的泛化建议；若命中店名、数字、价格、距离、营业时间、地址、评分或证据等敏感词，丢弃该模型文案并使用安全兜底。

## 指标采集准则

后续每个会改变检索、重排或模型调用行为的功能，都需要记录上线前后的指标；没有基线时先补采集，再讨论优化效果。

### 在线链路指标

- 端到端耗时，以及 `EXTRACTING`、`RETRIEVING`、`RERANKING`、`ANSWERING` 各阶段耗时。
- 模型调用次数、成功率、超时率、降级到本地规则的次数。
- 初始候选数、硬约束命中候选数、最终返回候选数、发生约束放宽的比例。
- 候选证据覆盖率：最终候选中至少有一条可引用证据的商户占比。

### 质量指标

- 约束解析有效率：模型输出能通过 JSON Schema 和业务校验的比例。
- 硬约束违例率：最终推荐违反预算、距离、营业时间或指定菜系的比例。
- 事实一致性：最终文案中的店名、价格、距离、营业时间和证据引用均能在候选结构化数据中验证的比例。
- 召回评估：有人工标注集后记录 `Recall@K`、`MRR`、`NDCG@K`，用于比较关键词检索、向量检索和混合检索。

### 当前已具备的指标

决策响应的 `trace` 和 `metrics` 已记录单次链路耗时、模型调用、候选漏斗、证据覆盖率和事实守卫结果。离线召回指标仍需标注集后实现。

### 2026-08-14 实现状态

`ai_decision_metric` 已记录单次决策的阶段耗时、模型调用成功/失败数、候选漏斗、放宽次数、证据覆盖率和事实守卫是否拒绝模型文案。离线 `Recall@K`、`MRR`、`NDCG@K` 仍需要人工标注集后才能计算。

## 2026-08-14：从单轮决策扩展为受控多轮状态机

### 现象

单轮接口在缺少位置时无法可靠执行“附近”或距离约束；严格条件无候选时，原实现会自动放宽菜系，用户无法确认系统修改了哪个条件。

### 处理

会话状态扩展为 `CLARIFYING`、`WAITING_RELAXATION`、`RESUMING`、`COMPLETED`。缺少位置时返回坐标补充问题；零候选时只返回后端预置的放宽选项，用户通过同一 session 明确选择后才恢复检索。每轮消息和每次尝试指标都独立落库。

“附近”有坐标时明确按默认 3km 解释，并写入 `softPreferences`；没有坐标时不猜测中心点，进入 `CLARIFYING`。

### 影响

系统不再静默放宽用户的核心限制，能够展示完整的“询问 -> 用户确认 -> 继续执行”闭环。用户界面后续只需把 `question` 和 `options` 渲染成快速回复即可。

## 2026-08-14：模型可观测性不等于输出原始思维链

### 处理

统一输出 `[AI]` 审计日志：状态、动作、约束摘要、候选数量、模型调用用途、成功/失败和耗时。全局 `com.hmdp` 日志级别改为 `info`，避免 SQL 调试日志淹没决策过程。

### 边界

不记录模型隐藏推理内容、API Key 或完整敏感上下文。日志记录的是可复核的动作和事实，例如 `CONSTRAINTS_PARSED`、`HARD_FILTER`、`WAITING_USER` 和 `DECISION_FINISHED`。

## 2026-08-14：模型输出与请求事实需要后端合并

### 现象

模型只接收自然语言查询，无法看到 HTTP 请求中的坐标，却可能在 `missingInformation` 中错误标记“缺少位置”。同时，模型生成自由推荐文案会重复店名、价格和距离，被事实守卫拒绝，增加一次无效模型调用。

### 处理

后端在约束提取后合并请求上下文：已提供坐标时移除位置缺失项；“晚上”默认归一为 19:00 并明确标注。自由文案调用默认关闭，仅保留工具化的约束提取和后端事实模板；若未来启用，必须通过事实守卫和指标验证其接受率。

### 指标基线

真实 DeepSeek 调用样本中，约束提取约 7.26 秒，受限自由文案约 1.50 秒且被事实守卫拒绝。关闭该调用后，预期每次决策减少一轮模型请求和约 1.5 秒延迟。

## 2026-08-15：续聊必须原子抢占暂停会话

### 现象

同一 `CLARIFYING` 或 `WAITING_RELAXATION` 会话若收到并发的续聊请求，两个请求都可能先读取到暂停状态，再分别继续执行。结果会导致重复检索、重复指标记录，甚至让后到请求覆盖先到请求的结果。

### 处理

续聊入口改为按 `session_id + 原暂停状态` 执行条件更新，只有成功将状态从暂停态迁移到 `RESUMING` 的请求可以继续。条件更新失败时立即返回“已被其他续聊请求处理”，不触发模型、检索、消息或额外的指标写入。

### 影响

会话从暂停状态恢复具备单执行者语义。客户端遇到该提示时应通过 `GET /ai/decisions/{sessionId}` 获取最新状态或结果，而不是盲目重试同一个续聊请求。

带登录身份创建的会话会在读取和续聊时校验 `userId`，防止其他已登录用户通过猜测 session ID 访问。为了保留匿名 Apifox 演示，匿名创建的会话暂不要求身份；若开放到真实公网，需要再引入不可猜测的匿名会话凭证。

## 2026-08-15：评测必须复用正式决策链路并保存逐例结果

### 处理

新增 `ai_evaluation_case`、`ai_evaluation_run` 和 `ai_evaluation_case_result`。固定用例保存人工标注的期望状态和商户 ID；每次评测通过正式 `ConsumptionDecisionService` 执行，保存对应 session、候选、状态、模型调用、证据覆盖和错误信息。

运行聚合 `Recall@K`、`MRR`、状态命中数、完成数、可验证的预算/距离硬约束违例数、事实一致数、证据覆盖率及模型调用数。单例失败不会中断整次运行，而是将运行标记为 `COMPLETED_WITH_ERRORS`。

### 指标边界

期望商户是人工维护的演示标注，不是线上用户点击标签。当前硬约束违例只自动验证响应中可复核的预算和距离；菜系与营业时间仍由召回链路保证，后续若要把它们纳入独立审计，需要在推荐响应中增加可验证的结构化字段。

### 架构取舍

评测层暂不依赖 Spring AI 或向量数据库。现有证据规模小，先通过固定测试集建立关键词/结构化召回的基线；当真实评论和标注集足够后，再在独立升级分支迁移 Java 17 与 Spring Boot 3，并比较向量或混合检索相对当前基线的增益。

模型菜系输出在进入召回前归一到当前数据集的词表，例如“港式茶餐厅”归一为“港式”、“寿司”归一为“日料”。这让模型同义输出不再影响硬过滤，并使约束评测能比较稳定的语义值而非表面字符串。

### 首次真实运行基线

2026-08-15，`ai_evaluation_run.id=1` 使用已配置的 DeepSeek 真实调用完成 3 条种子用例：状态命中 3/3、完成 3/3、模型调用成功 3/3、`Recall@K=1.0000`、`MRR=1.0000`、可验证硬约束违例 0、事实一致 3/3、证据覆盖率 `0.8900`。

第三条火锅低排队用例的三个候选中有两个带证据，因此该例覆盖率为 `0.67`；其余两例为 `1.00`，聚合后为 `0.89`。这是针对人工维护的 3 条演示标注的正确性回归基线，不应表述为真实用户流量下的推荐质量。

## 2026-08-15：状态机用例不能稀释排序和证据指标

### 现象

15 条扩展评测首次运行中，5 条预期为 `CLARIFYING` 或 `WAITING_RELAXATION` 的用例没有候选。这些用例被错误按 `MRR=0` 和证据覆盖率 `0` 计入全部 15 条样本，得到 `MRR=0.6333`、证据覆盖率 `0.5787`，不能代表已完成检索的推荐质量。

### 处理

新增 `rankingEvaluatedCount`。`Recall@K` 与 `MRR` 只对具有人工期望商户 ID 的排序用例计算；证据覆盖率只对实际返回候选的用例计算。状态机样本仍完整纳入 `caseCount`、状态命中、完成数和约束解析命中指标。

### 影响

状态控制质量与排序质量现在有独立分母，避免通过增加澄清/放宽样本人为拉低检索指标。运行 2 保留为旧口径的诊断样本；应用 V6 后重新运行，才可得到可比较的新口径基线。

## 2026-08-15：用证据覆盖指标驱动演示数据补齐

### 现象

按新口径，火锅相关排序样本的候选中商户 2 没有可引用证据，导致候选证据覆盖率低于 1。该问题来自演示数据缺失，而非模型或排序逻辑。

### 处理

V7 为商户 2 增加一条 `SEED_DEMO` 证据，内容限定为已有结构化营业时间和聚餐场景的可核对描述。来源继续显式保留 `SEED_DEMO`，不伪装成用户评论。

### 影响

重新运行评测后，当前 10 条排序样本应达到候选证据覆盖率 1.0。该结果只代表演示数据完整性提升，不代表真实评论覆盖率或 RAG 质量提升。

## 2026-08-15：评测运行必须记录实验版本

每个 `ai_evaluation_run` 现在保存模型名、检索策略版本和评测集版本。做稳定性复跑时，这三个条件应相同；做策略实验时，可以只改变检索策略版本，但模型、评测集和样本规模必须保持不变。不能将多个条件同时变化后的分数混为单一趋势。

## 2026-08-15：标注集合必须允许多个等价答案并输出约束差异

运行 4 中，“晚上 19:00 吃火锅”没有指定安静或低排队风险，却将商户 6 标为唯一正确答案；模型把商户 5、2、6 排序同样合理，导致 `MRR` 被错误惩罚。该用例修正为 `5,6,2` 三个可接受目标。

同时，约束评测失败此前只返回布尔值，无法定位字段。V9 新增 `constraint_mismatch`，列出 `cuisine`、`arrivalTime`、`occasion` 等未命中字段。菜系与约会场景均进行同义归一；“晚上”但未明确钟点时，后端统一为 19:00，避免模型任意推断不同晚餐时间。

## 2026-08-15：显式伴侣表达应由后端确定性补足约会场景

运行 5 的唯一约束未命中是 `occasion`：模型没有从“女朋友”抽取约会场景，但推荐正确。这说明模型提取不应成为用户明确表达的唯一解释来源。

后端现将“约会、女朋友、男朋友、情侣”统一补足为 `occasion=约会`，并在重排时对 `scene_tags` 中匹配约会的候选加分和输出可核对依据。该行为变更将检索策略版本更新为 `structured-profile-evidence-v2`，后续仅与同版本运行横向比较。

## 2026-08-15：评测运行记录必须按创建者隔离

### 现象

评测运行保存了 `user_id`，但 `GET /ai/evaluations/runs/{id}` 此前只按主键读取。任何已登录用户只要猜到递增的运行 ID，就可以查看其他用户的评测查询、推荐结果和模型调用信息。

### 处理

读取运行记录时增加创建者校验：调用方必须已登录，且当前用户 ID 必须等于运行记录的 `user_id`。未登录、历史匿名运行和非创建者统一拒绝访问，避免借由错误差异暴露跨用户运行数据。

### 影响

评测接口从“登录即可访问全部实验记录”收敛为私有实验记录。评测运行本身仍要求登录创建，因此不影响当前 Apifox 跑分流程；也不需要新增迁移。

## 2026-08-15：运行聚合必须提供有限的失败摘要

### 现象

单个评测用例捕获异常后会保存 `error_message`，运行状态也会变为 `COMPLETED_WITH_ERRORS`，但 `ai_evaluation_run.error_summary` 没有赋值。读取运行总览时无法判断失败规模和受影响样本，排查只能逐条展开结果。

### 处理

聚合完成时写入失败数量和最多十个 `caseId`，例如 `失败用例数=2，caseId=7,11`。总览不复制下游异常原文，原始诊断仍只保留在逐例结果中，避免把外部服务细节扩散到运行列表。

### 影响

失败运行可以在总览层快速定位，并保持错误详情的展示边界。该改动只使用已有 `error_summary` 列，不需要新增迁移或改变实验版本。

## 2026-08-15：实验指标需要受条件约束的自动比较

### 现象

每次运行都会保存分数和版本，但此前只能把两份 JSON 放在一起人工比较。容易出现一个常见误解：数据集、模型或检索规则已经换了，却把分数变化说成同一个算法“优化了”。

### 处理

新增 `GET /ai/evaluations/runs/{runId}/compare/{baselineRunId}`。它会先确认两次运行的模型、评测集版本、总用例数和排序用例数完全相同；任何一项不同都会明确拒绝比较。检索策略版本可以不同，因为它正是通常需要验证的变量；响应会用 `retrievalStrategyChanged` 明确标记这是否是一场策略对照。

通过校验后，接口返回当前运行相对基线的变化值，包括状态命中率、约束命中率、完成率、模型成功率、硬约束违例数量、事实一致率、Recall@K、MRR 与证据覆盖率。例如 `mrr: 0.0667` 表示当前平均排名质量比基线提高了约 6.67 个百分点；硬约束违例数量为负数才是改善。

### 影响

现在可以直接用接口证明一次变更的收益与代价，而不是口头比较。评测集内容发生改变时，必须同时提升 `evaluation_dataset_version`，否则接口只能保证版本标签相同，无法识别人工修改了数据库种子数据这一类流程违规。

## 2026-08-15：检索策略必须是可比较的实验变量

### 现象

对比接口第一版把“检索策略版本不同”也当成不允许比较的条件。这样虽然避免了混比，却会让最重要的问题无法回答：例如 v2 相比 v1，到底有没有提升约束识别或排序质量。

### 处理

将检索策略从固定条件改为唯一允许变化的实验变量；接口仍严格固定模型、评测集版本和样本数量，并返回 `retrievalStrategyChanged`。因此看到该字段为 `true` 时，可以把分数变化解释为“在同一模型和同一组题目下，检索策略的差异”，而不是笼统地说系统变好了。

### 影响

运行 5（v1）和重启后的 v2 运行可直接对照；但只要模型或评测集变化，仍必须建立新的基线，不能沿用旧结论。

## 2026-08-15：真实 v2 运行确认约束识别改善

### 现象

使用同一登录用户、同一模型 `deepseek-v4-flash` 和同一 15 条 `seed-v1` 评测集，运行 5（策略 v1）有 14 条约束命中；运行 6（策略 v2）为 15 条。对比接口返回 `retrievalStrategyChanged=true` 和 `constraintMatchRate=0.0667`。

### 结论

“女朋友/男朋友/情侣”由后端补足为约会场景的规则，在真实 DeepSeek 调用下带来 1 条、即 6.67 个百分点的约束命中提升。状态命中、完成数、模型调用成功率、硬约束违例、事实一致性、Recall@K、MRR 和证据覆盖率均未下降。

### 边界

这是 15 条人工维护演示用例上的一次策略对照，不能推断为线上用户总体提升。运行 5 与运行 6 尚未记录耗时，因此不能据此判断 v2 的性能代价。

## 2026-08-15：质量评测必须同时记录延迟 trade-off

### 现象

此前评测运行只保存质量、事实和模型成功率。即使某个策略让 Recall 或约束命中变好，也无法从历史运行回答“平均是否更慢”以及“最慢的少数请求是否变差”。

### 处理

V10 为每条评测结果保存总耗时与模型约束提取耗时；每次运行聚合平均总耗时、P95 总耗时和平均提取耗时。P95 可以简单理解为：把所有请求按耗时排序后，较慢的那 5% 请求附近的耗时，用于发现偶发长尾等待。

对比接口也返回三项耗时差值。正数表示当前运行更慢，负数表示更快；它们应和质量变化一起解释，不能只挑好看的指标。

### 影响

V10 前的运行 5、6 没有这些字段，因此不能补算真实延迟。应用迁移后，需要新跑一次 v2 作为带延迟指标的正式基线；若再验证 v1，则应临时切回 v1 配置、跑完后再切回 v2，且模型和评测集版本保持不变。

## 2026-08-15：真实延迟运行暴露降级规则和超时配置缺口

### 现象

运行 7 首次采集到真实延迟：平均总耗时 `4584ms`，P95 `5915ms`，平均约束提取耗时 `4565ms`。说明几乎全部等待来自模型调用，而不是数据库筛选或排序。

同一运行只有 8/15 次模型调用成功。第 6 条“附近 100 米的日料”走本地降级后，没有识别半径，错误地返回推荐而非等待用户确认放宽，导致状态与约束各少 1 条命中。

### 根因

本地规则只匹配“公里/km”，没有把“米”换算为公里。并且虽然配置文件写有 `ai.timeout-ms=20000`，客户端之前没有把这个值应用到 HTTP 客户端的连接和读取超时；配置存在但并未生效。

### 处理

规则解析现在识别“米/m”，例如 `100米` 转为 `0.1km`。OpenAI 兼容客户端改为使用配置的连接和读取超时。V11 还将模型失败次数写入逐例结果和运行总览；以后可直接看到失败率，而不必从“调用次数减成功次数”反推。

### 影响

运行 7 是重要的真实性基线：质量并非每次都稳定满分，模型服务波动会触发本地降级。修复后必须重新跑一次带 V11 的 v2 评测，验证降级路径能保持状态正确，并观察模型失败率与 P95 延迟是否改善。旧运行的失败次数无法补写。

## 2026-08-15：历史失败次数可由已有调用指标安全回填

### 现象

运行 8 的真实结果为 15/15 模型调用成功、状态和约束均为 15/15；平均耗时从运行 7 的 `4584ms` 降到 `4040ms`。但 P95 从 `5915ms` 升至 `6968ms`，表示整体更快时仍有少数请求更慢，这是需要保留的 trade-off。

运行 7 在 V11 之前产生。V11 新增 `model_failure_count` 时数据库给旧记录填了默认值 0，而运行 7 已保存的调用数 15、成功数 8 明确表明有 7 次失败。因此运行 8 相对运行 7 的 `modelFailureRate` 被错误显示为 0。

### 处理

V12 仅对“调用数大于成功数、失败数仍为 0”的历史记录执行 `调用数 - 成功数` 回填。对于当前单次决策链路，模型调用会被成功或失败二选一记录，因此这个差值可以安全还原历史失败次数。

### 影响

回填后运行 7 的失败次数为 7，运行 8 相对运行 7 的 `modelFailureRate` 应为 `-0.4667`，即失败率下降 46.67 个百分点。质量、耗时与推荐内容均不修改。运行 8 的 P95 变差不代表超时配置修复失败，而是 15 个样本下的单次长尾波动；需要更多重复运行后才可判断趋势。

## 2026-08-15：评测必须走完一次真实续聊，不能只测暂停

### 现象

旧评测只能证明系统会停下来询问位置或放宽条件，不能证明用户真的补充信息后，系统能继续执行并得到正确结果。

### 处理

V13 为评测用例增加续聊输入和期望最终状态。两条既有暂停用例会自动走完整流程：缺位置的附近日料补入坐标后应完成并推荐商户 8；附近 100 米日料无候选后选择扩大距离，也应完成并推荐商户 8。运行结果分别保存初始状态和最终状态，并把两轮耗时、模型调用合并。

### 影响

评测集升级为 `seed-v2`。旧的 `seed-v1` 运行不能与新运行直接比较；V13 后的首次真实运行将成为多轮、质量与延迟的新基线。

### 真实验证

运行 10 使用 `seed-v2` 完成 15 条用例，其中 2 条续聊均完成且最终状态命中。状态和约束均为 15/15，12 条完成、12 条排序用例的 Recall@K/MRR 均为 1，硬约束违例为 0。模型有 1 次失败，但本地降级仍保留正确结果。

平均总耗时为 `3680ms`、P95 为 `5178ms`，比运行 8 的单轮 `seed-v1` 不能直接横向比较，因为评测任务已增加两条完整续聊。用户曾在运行中强制关闭服务，因而可能留下 `RUNNING` 状态的历史运行；这不影响新运行，但当前版本尚未实现自动清理，属于后续运维改进项。

## 2026-08-15：中断的评测运行需要显式收口

### 现象

评测运行按条写入数据库。服务进程在中途被关闭时，已经创建的运行会保持 `RUNNING`，但它实际上不再执行，容易误导查看结果的人。

### 处理

新增 `POST /ai/evaluations/runs/{runId}/abort`。仅创建者可以将仍在 `RUNNING` 的运行标记为 `ABORTED`，并留下“运行被创建者主动终止”的摘要；已经完成的运行不能被改写。

### 影响

这是一种人工恢复机制，适合本地演示和开发环境。线上系统还应增加任务心跳和超时自动回收，避免依赖人工判断。

## 2026-08-15：重复真实运行验证正确性，同时暴露模型长尾

### 现象

运行 11 由开发端直接触发，仍使用 15 条 `seed-v2` 用例。状态和约束均为 15/15，模型调用成功 15/15，两个续聊均完成，说明运行 10 的正确结果不是单次偶然命中。

平均总耗时为 `4689ms`，但 P95 达到 `16724ms`，远高于运行 10 的 `5178ms`。质量指标稳定并不等于用户等待时间稳定。

### 结论

当前系统已经通过多次、多个类型用例验证，而不是只用一条问题测试；但 15 条人工维护用例仍是固定开发集，不能证明没有对这组题目过拟合。下一阶段应增加独立保留用例，且在产品层面为模型长尾增加超时与可见的规则降级提示。

## 2026-08-15：开发集与保留集必须分开

### 现象

`seed-v2` 已用于多次调试和修复，继续只在它上面获得满分，无法判断系统是否只适配了这 15 条固定表达。

### 处理

V14 为用例增加数据集版本，新增 `holdout-v1` 的四条独立表达，并提供 `POST /ai/evaluations/runs/holdout`。保留集覆盖“带对象/牛排”“寿司/100米”“寿司/低预算”和“尽量别排队”等不同说法，其中一条仍走完整放宽续聊。

### 边界

保留集规模仍小，只能作为演示项目的独立冒烟评测，不能替代线上随机流量或大规模人工标注。保留集出现失败时，应先记录并分析原因，再决定是否将该表达转入开发集；不能一失败就直接修改规则后仍把它称为保留集。

### 真实验证

运行 12 在 `holdout-v1` 的 4 条独立表达上完成：状态和约束均为 4/4，包含 1 条完整放宽续聊，三条排序用例的 Recall@K/MRR 均为 1，模型调用成功 4/4，平均耗时 `4050ms`、P95 `5842ms`。这支持系统对当前同义表达有一定泛化能力，但不能把 4 条保留题的满分表述为线上泛化能力证明。

## 2026-08-15：暂停会话需要允许拒绝、结束和地点名输入

### 现象

此前“附近”缺坐标时，用户只能提交定位；不愿授权定位会永远卡在澄清状态。暂停期间若发送无关文本会报参数错误，但旧会话仍保持等待。地点名称也不能直接用于检索。

### 处理

`CLARIFYING` 增加“按全城搜索”和“结束本次推荐”选项。前者移除附近/距离硬约束并留下审计偏好，后者将会话收口为 `CANCELLED`；任意自由文本续聊也按结束旧会话处理，避免误把跑题内容当作放宽请求。

增加可替换的演示地点解析表：`西湖文化广场`、`运河上街`、`武林广场` 会在未提供坐标时转换为固定演示坐标。真实地点名解析需要接地图地理编码服务、服务 Key、候选消歧和隐私授权，因此当前明确只是 mock，不声称覆盖任意地点。

### 影响

用户的主流程不再被定位拒绝或跑题卡死。生产化时应将演示地点表替换为受限的地理编码适配器，并让客户端展示候选地点供用户确认。

### 定位拒绝后的真实验证

用户拒绝定位后，系统正确按全城完成推荐且没有再次调用模型。响应中曾残留“附近”为硬约束、并提示缺少位置，和全城降级相互矛盾；现已在降级时同步移除附近/距离硬约束和位置缺失项，确保约束、答案和实际检索范围一致。

地点名称 mock 已成功将“武林广场”转换为演示坐标并完成检索。由于演示坐标可能恰好与某商户坐标相同，答案现在会明确说明距离仅用于演示，避免把 `0.0km` 误读为真实地图结论。

### 自动化回归保障

上述流程不能只依赖一次 Apifox 人工验证，因此补充了两条服务层自动化测试：一条确认用户选择“不提供位置”后，系统确实按全城搜索，并同时清除“附近”和“缺少位置”这些已经失效的信息；另一条确认用户在暂停会话中发送无关文本时，会话变为 `CANCELLED`，且不会再查询商户或继续推荐。

这样以后即使修改状态机，测试也会先指出“界面显示的约束”和“实际检索策略”是否重新发生矛盾。这里测试的是业务规则，不依赖 DeepSeek 或真实数据库，所以可快速重复执行；真实接口验证仍用于确认网络、数据库和模型调用的集成结果。

## 2026-08-15：规则兜底不能悄悄伪装成模型成功

### 现象

模型约束提取超时或失败时，系统本来会用本地规则继续完成检索，这是为了避免一次外部服务故障就让用户完全得不到结果。但旧响应只有 `usedModel=false` 和内部计数，调用方不容易看出本次是否经历了降级。

### 处理

`DecisionResponse` 新增可选的 `degradedReason`。只要本次存在模型调用失败，响应会说明“模型约束提取未成功，本次已使用本地规则继续处理”。正常成功请求不新增该字段；推荐、证据和最终答案仍完全由后端事实生成，不会因降级而换成模型编造的文本。

### 影响与验证

这让前端可以据实提示用户，也让评测中的 `modelFailureCount` 与单次接口响应形成对应关系。单元测试分别覆盖“模型异常进入规则解析”和“失败指标映射为对外降级说明”；完整聚焦测试集通过。要人工验证该字段，不能故意填错生产 Key，应该在隔离环境模拟超时或服务端错误。

补充审查发现：缺少 `DEEPSEEK_API_KEY` 时，客户端会在发网络请求前直接进入规则路径，这不是一次真正的模型调用，因此也不应伪造 `modelFailureCount`。响应现在单独返回“未配置模型服务，本次已使用本地规则处理”，把“没有尝试调用”与“调用失败”区分开；两种情况均有自动化测试。

## 2026-08-15：从单次推荐扩展为嵌入点评业务的多轮工具 Agent

### 现象

原有 Agent 的模型职责主要是一次约束提取。推荐完成后，用户继续询问“还有别的吗”“这家有优惠券吗”“评价如何”“两家怎么比较”时，原接口没有可恢复的业务上下文，也没有让模型选择已有点评业务能力的入口。

### 处理

新增独立的 `POST /ai/decisions/{sessionId}/conversations` 入口，仅允许已完成推荐的会话追问。会话上下文保存当前聚焦商户、已展示商户和轮次，避免“这家”或“还有别的吗”脱离前一轮推荐。

新增 `BaseAgentTool` 统一工具协议和只读工具注册表。首批工具为：

- `search_alternative_shops`：排除已展示商户后继续查找备选；
- `get_shop_detail`：查询商户均价、评分、营业时间和地址等事实；
- `query_shop_vouchers`：复用优惠券和秒杀券查询，只读返回规则、库存与有效期；
- `search_shop_evidence`：关联 AI 演示证据、探店笔记及笔记评论；
- `compare_shops`：返回两家商户的可验证事实对比。

模型通过 OpenAI 兼容 Tool Call 在最多 3 步内选择工具和参数；后端负责参数解析、权限、执行和最终事实模板。每次工具调用输入、输出、状态和耗时写入 `ai_agent_tool_call`，会话上下文写入 `ai_decision_session.agent_context_json`。模型不可用或规划失败时，按有限本地意图路由到同一批只读工具，并在响应中明确降级原因。

### 边界

这一阶段不允许模型直接调用领券、秒杀下单或任何写操作。后续若接入交易工具，必须先实现显式确认、登录态校验、幂等键和订单结果复核。工具返回的评价证据目前仍包含 `SEED_DEMO`，不得表述为真实线上评论。

### 数据与评测后续

为支撑评价、探店笔记和券的多轮演示，需要在后续 `V16__agent_business_demo_data.sql` 中补充餐饮商户、画像、演示证据、笔记、评论和券数据，并保持跨表商户 ID 一致。下一轮评测应新增多轮任务用例，记录工具选择、工具参数、证据引用、跨轮指代、工具失败率、总步骤数和端到端耗时，不能只复用推荐阶段的 Recall/MRR。

### 2026-08-15 数据落库验证

`V16__agent_business_demo_data.sql` 已补充 36 家餐饮商户、36 条画像、216 条 `SEED_DEMO` 证据、36 篇探店笔记、108 条笔记评论、42 张普通券和 12 张秒杀券。脚本首次执行暴露两个生成数据常见问题：MySQL 命令行需显式使用 `utf8mb4` 才能正确写入包含扩展汉字的商户名；评价证据被拆成两段 `INSERT` 时，前一段遗漏结束语句和幂等更新子句。修复后从头重跑，实际表计数与预期完全一致。

这批数据均为本地构造演示数据，`ai_review_document.source_type` 统一为 `SEED_DEMO`。它用于验证工具链的跨表关联和事实引用，不能对外表述为真实线上评价、券库存或商户经营数据。

## 2026-08-15：增加可操作的 Agent 调试界面

### 现象

此前首轮推荐、多轮业务追问和工具审计只能通过 Apifox、curl 或控制台调用。接口虽然已闭环，但难以直观看到 `CLARIFYING -> COMPLETED -> 业务工具追问` 的状态切换，也不利于项目演示。

### 处理

在配套 Nginx 实际静态目录 `nginx-1.18.0/html/hmdp` 新增 `agent-console.html` 和局部样式 `css/agent-console.css`，复用既有 Vue 2、Element UI、Axios 依赖以及 `/api -> 8081` 代理：

- 左侧提交消费需求、可选坐标和候选数；
- 中间按会话顺序展示推荐、澄清选项和完成推荐后的自然语言追问；
- 右侧展示会话状态、首轮指标、模型降级原因，以及从 `GET /ai/decisions/{sessionId}/tool-calls` 读取的实际工具审计记录；
- 原点评首页增加 Agent 入口，不替换既有首页、商户和博客页面。

### 边界

该页面是本地调试与项目演示台，不是面向消费者重新设计的点评首页。它依赖现有登录态；未登录时仍沿用公共 Axios 拦截器跳转登录。业务追问仅在推荐会话达到 `COMPLETED` 后可用，前端不会绕过后端状态约束。

### 调试发现：AI 请求不能复用普通列表的短超时

原配套前端把 Axios 全局超时设置为 `2000ms`。普通商户列表适用该值，但首轮 Agent 可能包含模型约束提取和检索，超过两秒会被浏览器主动取消；原错误拦截器还默认 `error.response` 一定存在，使超时异常被二次抛出而没有用户可见提示。

调试页的三个 AI 写请求现在显式使用 `30000ms`，不改变既有列表接口的超时体验；公共拦截器则先检查响应是否存在。30 秒只是演示环境的前端等待上限，正式环境仍应配合后端模型超时、熔断和降级策略，而不是无限等待。

## 2026-08-15：调试页收敛为 Chatbot 一问一答

### 现象

首版调试页同时提供左侧表单、会话区和审计侧栏，交互上更像 API 控制面板而不是消费决策助手。更严重的是公共 Axios 拦截器返回 `Result` 外层对象，页面却把它当作业务响应使用，导致后端在 `CLARIFYING` 状态返回的 `question` 没有被正确读取，界面错误地显示为“已完成处理”。

### 处理

页面改为单一 Chatbot 会话：第一句话创建推荐会话，完成推荐后同一输入框发送业务追问。每条助手消息下直接展开本轮过程：首轮展示 `EXTRACTING`、`RETRIEVING`、`RERANKING`、`ANSWERING` 的耗时与摘要；追问展示实际 `toolName`、返回摘要和耗时。调试原始请求和响应仍交给浏览器开发者工具，不再占用业务界面。

澄清选项作为聊天内快捷操作显示。用户选择提供位置时，页面调用浏览器定位并将坐标连同 `PROVIDE_LOCATION` 一并提交；拒绝定位则按现有状态机走全城搜索。所有接口响应先解包 `Result.data` 后再更新会话状态，避免外层响应对象与业务 DTO 混用。

## 2026-08-15：在推荐和工具调用前增加消费意图门禁

### 现象

`POST /ai/decisions` 过去只检查文本非空，`你是？` 这类能力问答也会创建决策会话。约束提取为空后，召回和重排仍会从全部商户中给出默认推荐。已完成会话的业务追问入口同样会把无关内容降级为商户详情查询，导致不必要的工具调用和错误回答。

### 处理

新增确定性的 `ConsumptionIntentGate`。它优先识别能力问答，再识别本项目支持的餐饮消费决策和商户事实关键词。首轮未命中消费意图时返回 `UNSUPPORTED` 和范围说明，不创建会话、不调用模型、不召回商户；完成会话后的无关追问只写普通会话消息，不调用业务工具。首轮和追问分别增加回归测试，验证不会持久化决策或工具调用。

### 边界

这不是通用闲聊能力，也不应将一切文本发送给模型判别。当前关键词门禁的目标是保护餐饮 Agent 的业务边界并保证可解释、低成本；后续支持更多消费品类时，需要随支持范围增加词表与独立测试用例。

## 2026-08-15：改为模型驱动的对话编排，而非关键词拦截

上一版关键词门禁虽然阻止了“你是？”触发商户召回，但错误地把普通闲聊变成了拒绝回复，且用户不能自然离开或重新进入消费流程。该实现已撤回。

新增 `POST /ai/chat/messages` 统一入口。模型通过 Function Call 在 `GENERAL_CHAT`、`START_DECISION`、`BUSINESS_FOLLOW_UP`、`EXIT_DECISION` 之间选择路由：闲聊由模型正常回复；消费需求才创建决策；已完成推荐后的商户问题才调用业务工具；在位置/放宽条件的等待状态中转聊或明确结束，会先取消暂停决策再回到闲聊。模型不可用时保留有限本地路由作为降级，并在响应中声明。

前端 Chatbot 现在只调用该编排入口，保留已有澄清按钮用于提交结构化位置和放宽选项。Spring AI 没有在本阶段引入：当前项目已有 OpenAI 兼容客户端和 Function Call 协议，路由状态机才是本轮的核心变化，额外框架不能替代这层业务编排。

### 运行排障

普通聊天连续返回相同本地文案时，应先检查 `ChatMessageResponse.usedModel=false` 及 `degradedReason`。该分支表示运行中的 Spring Boot 进程没有读取到 `DEEPSEEK_API_KEY`，与另一个终端窗口是否设置变量无关。使用 IDE 启动时需在对应 Run Configuration 配置环境变量后重启；路由和闲聊的模型调用失败也会输出 `[AI][chat]` 的 `CHAT_ROUTING` 或 `GENERAL_CHAT` fallback 日志，便于区分未配置与上游调用失败。

### 本地配置隔离

`application.yaml` 只保留环境变量占位符，不再保存数据库、Redis 或模型凭据；默认激活 `dev` profile。被 `.gitignore` 忽略的 `application-dev.yml` 覆盖本地数据库、Redis、模型地址、模型名和 Key。模型日志中的 `401 Unauthorized` 表示请求已携带 Key，但上游拒绝认证，通常是 Key 无效、过期、复制错误，或 Key 与所配置的服务地址不匹配；它不同于未配置 Key。开发机应在本地 `application-dev.yml` 填入有效 Key 后重启，不应提交该文件。

## 2026-08-15：工具追问的超时降级与全链路可观测日志

### 问题与根因

一次“这家评价如何”的追问依次经过对话路由和 `AGENT_TOOL_PLANNING`。旧实现允许工具执行后继续进行最多三轮规划；而每轮规划复用 30 秒模型读超时，前端请求也恰好是 30 秒。因此当第二轮无意义的规划遇到模型长尾时，浏览器会先取消请求，页面只能显示“请求失败”，即使后端稍后本可以按本地工具回退。

### 调整

追问现在每轮只进行一次工具规划，模型给出第一个只读工具及参数后立即执行；不会为了获取最终自然语言而再次进行工具规划。规划超时独立限制为 8 秒，超时、空规划或模型异常后按既有本地意图路由调用同一批只读工具，确保用户仍收到数据库中的事实。规划成功后可选地以 8 秒短超时调用 `AGENT_ANSWER_POLISH`，只允许将已检索事实整理为自然语言；润色失败保留原始事实答案，不会导致整轮失败。

`OpenAiCompatibleClient`、对话编排和工具执行增加了结构化日志，能够串起 `query -> CHAT_ROUTING -> TOOL_PLAN(arguments) -> TOOL_START -> TOOL_SUCCESS(result) -> ANSWER_POLISH_SUCCESS`。异常则记录具体阶段、会话、轮次、异常类型和压缩后的错误信息。日志不输出 API Key，模型输出和工具事实会截断，避免单条日志无限膨胀。前端聊天和澄清请求等待上限调整为 45 秒，并能区分浏览器等待超时与后端业务错误。
