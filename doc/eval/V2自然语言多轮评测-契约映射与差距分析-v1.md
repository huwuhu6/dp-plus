## 2. 分类及可复用断言

分类针对**每项完整业务义务**，不把某个相关字段通过等同整项通过。A：当前投影/断言直接证明；B：已有谓词可组合，但要准备独立固定事实、前后快照或固定身份；C：仍缺关键观察/表达，需要小范围评测扩展；D：当前外部资料或主观标准不足，不宜完全自动评分。表中主类只有一个，另列能先验证的部分；C/D 不意味着该项全部不可观察。所有引用类都先验证真实可见上下文。

### 2.1 现有表达能力与限制

| 目标 | 优先复用方式 | 不能据此推出 |
| --- | --- | --- |
| 继承/替换/取消 | 两轮 `criteria.cuisine.include/exclude`、`criteria.location.*`、budget、distance、preferences 与 `semantic.cleared`；已知固定条件可逐字段 equals | cleared 含 CUISINE 只证明解释有清除；冷面关键词出现不证明旧火锅必需消失，必须查最终 criteria 与执行候选 |
| 时间/人数/形态 | `criteria` 整体 equals 可包含实际 DiningCriteria 的 diningTime，`criteria.preferences.values` 整体 equals 可含人数等偏好 | validator 不接受 `criteria.diningTime.arrivalTime` 子路径，但可通过整个 criteria 校验，不是时间完全不可观察；自由文本不能仅靠关键词证明语义/OR/强弱 |
| 当前列表序号 | expectedRelations 的 `groundedOrdinal/EQUALS_VISIBLE`，fromTurn 指向已核验列表；固定 ID 时 equals/contains 完整 groundedEntities | 仅证明至少一条请求绑定命中，不保证所有请求均正确、名字序号一致、回答使用同店事实；不覆盖反馈绑定 |
| 选择与反馈 | selectedShopId null/equals、semantic.requestKinds、feedbackKinds，ledger/拒绝列表精确 equals | selected 为 null 不能证明已积极承接反馈；REJECT 列表是 task 范围，并非全用户永久黑名单；根 focusedShop 为空不能证明没有 V2 聚焦 |
| 本批其他选项 | recommendations DISJOINT 或 finalCandidates 固定 ID 集合；ledger + rejectedShopIds + cuisine.exclude 精确比较 | DISJOINT 要两轮都非空，因此无供给时无法使用；它不证明楼层正确或“没有永久排除” |
| 执行与硬验证 | executedActions 精确 equals，verificationStatus、hardConstraintsVerified、verificationFailures | 动作成功不代表目标问题有答案；VERIFIED_PASS 只覆盖 E14 已执行检查；EMPTY 与事实未知不能靠一个 COMPLETED 混合评分 |
| 错误和未验证 | E6/E18 保证错误断言/异常失败，缺 outcome 的 matched=null | 无义务级未验证记录；无所有可选断言时 Case 仍可能无失败完成。现有 null 不等于业务通过，缺断言项不能被汇总吞掉 |

equals 对对象要求整体相等；contains 对 Map 可以递归部分匹配，对 List 却要求一个完整元素相等（E4）。不能写 `groundedEntities.0.shopId` 或 `tasks.<动态ID>.criteria`，也不能假装存在 notContains、比较大小、OR、任意路径 SAME/CHANGED。用整个已知集合 equals/固定合法候选集合可避免新增操作符，但真实输出顺序/措辞多解时要保留人工验收，不能为适配 equals 强制唯一实现。

expectedToolsByTurn/candidateFrom 能记录工具名、参数与源轮序号（`AiConversationEvaluationService.java:790–840`），但工具相关 matched 不进入 hasFailure（E6），且 V2 未必产生旧 decision-session 工具记录。不能把它作为本轮严格业务通过的唯一依据。绑定检查应先复用 V2 outcomes/relations；实际工具目标需要可靠的只读观察，且接受缓存/已有事实等合理路径。

### 2.2 逐项表的准备和扩展代号

- **P0**：冻结项目清单、核心项、分支、计划分母；门控实际展示/顺序/身份/日期/位置，无隐藏聚焦。
- **P1**：独立审核的候选事实清单（固定测试资料或有来源真实资料），记录门店/商品/单位/有效时刻/未知范围；从事实导出合法候选集合，不能从输出倒推答案。
- **P2**：保存前后有效条件、全部任务与批次；在受控层可以使用稳定 ID，端到端保留动态身份。
- **X1**：最小只读全任务/历史批次投影、criteria 时间子路径白名单；可选 taskId SAME/CHANGED，禁止以 decisionSession 代替任务。按源轮动态 ID 选择目标任务以查旧安排。
- **X2**：保留完整响应和候选 DTO；只读记录请求—绑定—执行观察对应（目标、事实种类、返回值/未知、证据来源），含反馈对象。现有事件不足的部分仅由隔离测试观察器捕获实际调用/返回值，不改业务分支、不伪造事件。
- **X3**：业务项与多条现有断言的关联、核心标记、前提/证据状态及结果侧表；先可采用版本化映射与独立汇总，不必改数据库实体或重建框架。必要动态身份关系只增加严格、有限类型。

这些是下一阶段设计，当前不存在对应新字段或 API。X2 不要求 LLM 自评或 Production 新增医学/菜单能力；缺真实事实时仍记未知/未验证。最终回答的语义完整性先人工审核，补完整记录不自动意味着通用自然语言评分已实现。

### 3.17 如何理解分类数量

全部 53 MUST、40 MUST NOT 均已映射，按完整项目主类计：A 0、B 27、C 60、D 6。完整义务均需要额外上下文/事实组合或仍缺观察，不能单靠一个现有字段证明；多数完整项目含回答/证据/范围等子义务，故主类 C。这不否认已有直接可用的 A 级子断言：如 null 未选店、精确候选 ID、固定条件值、CLARIFYING、显式验证状态，以及已核验列表上的 ordinal 身份。B 项须连同 P0/P1/P2 组合后才形成业务证明。本表不是通过率，不把 B 当作已经运行成功，也不把 C/D 判成 Agent 已失败。

## 4. 三种跨轮能力的具体边界

### 4.1 条件连续性与覆盖

固定上下文中的继承、替换、取消，可复用 expectedV2Outcomes：核对前后完整有效条件；显式值、空与notSet分开；再查实际候选是否适配。原约束被自由文本转移到preferences时，不能只证明 cuisine.include 不再火锅就认为已取消火锅必需。执行实际SearchSpec的只读捕获能排查“状态对、执行仍用旧条件”，当前executedActions不保存spec（E3/E12）。

不相关条件保持可用多个字段或整个criteria equals表达，已知常量无需增加新关系。动态任务ID的连续性才需要最小 taskId SAME/CHANGED；两端必须存在有效身份，ERROR轮不能满足，关系失败必须影响Case。decisionSession不是task identity，V2响应也未保证有旧sessionID。

独立安排隔离需要同时观察今晚/明天两task的条件、反馈和选择。仅看taskCount=2、taskDirective=START_NEW或活动criteria无法证明旧任务未污染，也无法证明同轮反馈写到正确旧任务。X1应复用已有tasks数据，按源轮taskId读取旧安排；没有必要设计第二套任务模型。跨轮 compare只比较冻结的业务相关字段，允许合理生命周期变化，不能要求整个memory字节相同。

### 4.2 商户引用

当前ordinal关系可严格拒绝22绑成11，但它使用fromTurn持久化最后批次，不直接确认用户界面实际收到并显示了该顺序；必须先核对响应候选和展示记录。工具/事实返回还需对应同一个请求。多请求场景不能满足一个正确绑定就放过其他错绑。

名字与序号同时出现时，应独立验证两条线索一致：正常S06不需要逼用户再确认；冲突时需要澄清。当前模型引用类型分别为OrdinalRef或NamedEntityRef，解析摘要不保留足够信息证明交叉验证；评测可以从冻结显示名单独立核对，生产是否做到要单独记实际结果。

历史批次**已有存储**，现有fromTurn1的ordinal关系也能从旧快照比较B的ID，无需先新造历史存储。但任务/批次明细未公开，且Grounding只收到该任务最新批次。X1增加只读历史投影用于前提门控和诊断，X2建立request对应；不会使Production自动获得历史查询能力。验证历史查询不恢复条件时，还要比较第三轮当前有效偏好，不以RESTORE作为答案。

无法定位时CLARIFYING是有用但不足的谓词：同样状态可能在澄清城市而非商户。最终须核对澄清主题和没有无据绑定/确定地址。未知事实不应被误判为未知商户身份。

### 4.3 反馈与意愿

“看着不错”：有正确目标的反馈账本 +未产生选择效果/未宣称最终选定；“就去第一家”：明确选择目标 +仍回应楼层。selectedShopId只是证据之一，不要求所有合理实现都以特定字段响应。当前编译器已有Select与Feedback分离，组件测试证明枚举/效果边界，不能证明原话被正确解释。

“不辣就去”：同时检查第二家、主要餐食、证据可信与最终不辣、条件是否成立、意愿承接和回答。不得以conditionalCriteriaApplied（条件修改需求）替代guarded select（条件执行选店）。当前typedValue没有辣度，guard计数与SKIPPED不能说明其正确谓词；未知分支未选店只能算局部正确，不能替代完整回应。

“本批不喜欢”：ledger应保留批次与范围，替代结果不立即重复；rejectedIDs/菜系exclude不应无依据扩张。task范围实体REJECT并非全用户永久黑名单，不能因字段名包含Rejected就误判，也不能因本轮未重复就证明无永久污染。无法观察其他安排/用户长期状态时记未验证。

## 5. 前提建立：Fixture 与真实端到端

现有JSONL只有逐轮消息与可选设备位置/选项，能请求推荐，不能保证输出指定类别、数量、顺序、商品、历史B或不同D/E；无上下文种子、冻结时钟、事实分支、动态前提gate。notes不能建立数据前提。题目写“第二家是米线”不等于真实响应第二家已是米线；预算/地理可能让首轮为空，必须先判覆盖（E1/E7/E16）。

### 5.1 测试隔离边界与最小方案

优先在JUnit/test profile中替换WorkingMemoryVersionService、ChatMemoryService底层存储及只读商户/工具/位置依赖；与已有Mock/OCC测试结构保持一致，但保留真实Grounding、reducers、compiler、executor和renderer。测试种子不是新增用户操作，不通过伪造消息声称真人点选，不篡改生产持久化状态。若要测真实持久化，使用专用测试数据库/Redis命名空间、独立chatId及归属，不覆写真实用户chatId；种子API只能在测试作用域内，不暴露生产入口。

固定首轮检索结果并通过真实POST创建批次，比直接种memory更容易保持显示与状态一致，但验证不到首轮实际召回能力；种memory更便于历史双批场景，必须额外校验历史、任务、批次一致。两者都能使用现有批次模型，无需增加Production“测试商户”逻辑。Mock预设最终ChatMessageResponse只能测试评测器，不能用于证明待测Agent业务正确。

首次建议**混合但分账**：A建立诊断明确的受控多轮基线；B记录全部计划场景的首轮就绪及真实链路结果。不能拿A的固定推荐成功填补B的首轮覆盖失败。针对B没有就绪的场景，仍保留未就绪项目和能独立验收的原轮业务项；可以另做A诊断，不能替换原B运行记录。

### 5.2 事前冻结与复现记录

逐场景冻结：规范/映射版本、核心项目ID、目标A/B事实分支、商户/商品/批次预期、地点/时区/参考时刻、资料来源及有效范围、OR与近似/主观裁定、运行计划及重复次数。C04需实际形成A停车困难答复；C15需两批真实不同且B存在；C06需旧task身份和日期；S13需核实没有额外聚焦；C23需主餐而非饮料及减辣边界。

逐运行保存：HEAD、配置摘要（无凭证）、模型标识/参数、依赖资料版本、完整请求响应、每轮任务/批次身份、条件/反馈/绑定/执行观察、前提gate证据、逐项判定与原因。模型有随机性时记录种子（支持时）与重复计划，不能保证字节重现，但证据与判定必须可重放复核。保留失败与未知，人工复核关键事实/回答，不以模型自评作唯一证据。

## 6. 统计契约与最小评测改动

### 6.1 分母和状态

与业务规范1.4同步：计划场景数N、成功建立预定前提数R、就绪且核心验收通过数P、所有适用项目完整判定数F。分别记录R/N、P/R、F/N；同时报告原始数量、失败数、验收未完整数、首轮覆盖失败数及准备失败数。R=0时P/R不适用。F包含证据齐全的业务失败，不是正确率；P中的场景可能还有额外事实未验证，因此P不一定等于F。全部项目充分判定才算F，已知一个失败不足以宣称其余都已验证。

每个项目记录 sceneId/itemId、M/F与核心标记、轮次、适用性、冻结事实分支、前提是否成立、观察对象、证据定位、满足/不满足/未验证/前提不满足/不适用、原因。禁止项满足表示未发生所禁止的错误，必须有覆盖其行为边界的证据，不能默认没记录就是没发生。

原因分别为准备条件未建立、真实首轮覆盖失败、前提成立后业务违例、可独立验收的事实未知、不足观察证据；执行错误和评测基础设施错误另列。基础设施错误既不计业务通过，也不把所有项目自动记业务失败；待定项目未验证，已成立失败证据保留。所有计划场景进入清单，重跑须保留原记录，不能删失败取最佳输出。

现有completedCount、v2OutcomeMatchedCount及COMPLETED_WITH_ERRORS不能直接代替P/F或就绪率；outcome count以“某轮断言组”为单位，不是MUST个数。E6的hasFailure用于现有机器case，不代表已完整执行业务规范。下一阶段先用X3结果侧表实现这套口径即可，不要求改现有数据库统计结构。

### 6.2 最小能力集合与取舍

| --- | --- | --- |
| 1 | P0/P1/P2与X3版本化映射、前提gate和逐项结果侧表 | 先解决无法定义分母的问题；明确未验证不能通过。先人工表亦可，首次基线无需通用评分引擎 |

### 7.1 可定位的静态路径，不冒称模型复现

1. **C15历史批次**：同task第一批B、第二批D/E已正确存储 → `view`只给最新D/E → NamedEntityRef只搜最新 → B无法grounding而澄清；现有Earliest TaskSelector选的是task，不是该task第一batch。旧B仍在memory，属于业务引用限制，不是场景准备没B。建议后续业务任务研究历史身份查询与当前条件分离，本轮只投影与记录。
2. **C06跨安排反馈**：若语义同轮是START_NEW、反馈OrdinalRef(2) → lifecycle创建新task → grounding在空新task解析反馈 →澄清且未提交；或反馈归属缺正确旧context。该输入路径在源码确定存在，但未用原话/真实模型复现，不能断言每次都会这样。即使语义不走此路径，评测只看active任务也不足以判旧安排反馈。
3. **C23事实guard**：事实请求落DETAIL/EVIDENCE →工具没有稳定辣度typedValue →条件不满足可执行观测；正确guard应暂缓，而无法正向确认不辣主餐。关系计数正确不能补事实。后续业务能力另评，测试不能返回假真值伪装现有工具已支持真实菜单。
4. **多个事实/选择同时返回**：response循环对每个非general generalAnswer赋值fact，后值覆盖前值；renderer优先recommendations，其次fact，其次selected →C15两事实可能仅展示最后一个，S10有fact时选择承接文本可能不显示。源码表明有信息丢失路径；原话是否触发还需后续受控实际执行。评测需完整response发现，不应修改用户预期或只检requestCount。
5. **上下文与事实强度**：SemanticInterpreter模型只看当前userTurn，C04“那算了”停车原因、C10“那个烧鹅”历史来源等不能假定模型已看history；HH:mm营业放行及偏好字符串证据也不能保证日期/菜单真实性。记录这些观察以解释基线，不把未跑场景判为已失败。

上述是代码审计的确定控制流/能力限制及待实验验证影响，没有宣称得到16场景的实际模型失败率。业务改进属于下一轮授权范围；评测补足观察可以将失败正确定位，但不会使这些能力自动通过。
