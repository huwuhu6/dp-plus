# 套餐券部分核销与退款可靠性开发记录

更新时间：2026-08-20

## 1. 为什么不沿用原订单表

原 `tb_voucher_order` 一行只代表一张券，只有整单 `status`、`use_time` 和 `refund_time`。它只能表达“这张券已核销”或“这张券已退款”，无法表达一笔套餐购买 3 张券后“已核销 1 张、退款 1 张、还有 1 张待使用”。给原表增加 `used_count` 也不够：无法定位哪一张券被核销、无法审计重试、也无法让核销与退款在同一张券上竞争。

真实本地生活平台会暴露部分使用和部分退款状态。美团企业订单接口包含未使用、部分使用、已使用、已退款、部分退款等状态；抖音本地生活也明确支持一笔订单多张券时，仅退款未核销券。此处只实现一个受控 MVP，不接支付渠道、自动过期退款、跨门店和商家结算。

## 2. 模型与状态边界

新增表，不修改旧 `tb_voucher_order`：

```text
tb_voucher_package_order（一笔已支付套餐订单）
  └─ tb_voucher_certificate（N 张可独立履约的券实例）
       └─ tb_voucher_fulfillment_audit（核销/退款请求审计）
```

单张券实例只有三种状态：

```text
UNUSED -> USED       商户核销
UNUSED -> REFUNDED   用户退款
USED   -> UNUSED     原核销门店在 60 分钟内撤销误核销
```

订单状态不是客户端传入，而是由券实例聚合：

| 券实例组合 | 套餐订单状态 |
| --- | --- |
| 全部 `UNUSED` | `PAID` |
| 部分 `USED`，其余未使用或退款 | `PARTIALLY_USED` |
| 部分 `REFUNDED`，其余未使用 | `PARTIALLY_REFUNDED` |
| 全部 `USED` | `USED` |
| 全部 `REFUNDED` | `REFUNDED` |

撤销不是把状态随意回退：仅原核销门店可发起，且必须在核销后的 60 分钟内完成。超过窗口则保留已核销事实，后续应走结算后的人工售后或对账流程；本项目不把它伪装成通用退款。

## 3. 可靠性方案

### 3.1 并发裁决

核销和退款都使用 MySQL 条件更新：

```sql
UPDATE tb_voucher_certificate
SET status = :targetStatus, used_time/refunded_time = NOW()
WHERE id = :certificateId AND status = 'UNUSED';
```

影响行数只能是 0 或 1。两个店员同时核销同一张券，或核销和退款同时到达时，只有一个请求能从 `UNUSED` 成功迁移。这里不依赖 JVM 锁、Redis 锁或“先查再写”的乐观假设；数据库是履约事实的最终裁决者。

### 3.2 网络超时重试幂等

`tb_voucher_fulfillment_audit.request_id` 有唯一索引。服务先只读定位券实例，再插入 `PROCESSING` 审计行以抢占请求号；相同 `requestId` 的重试不会再次修改券状态，而是回放已记录的成功或拒绝结果。若原请求事务回滚，审计抢占也一起回滚，后续重试可安全重新执行。

### 3.3 权限与审计

履约接口要求现有登录 token；请求体的 `userId/operatorId` 必须等于 token 用户，不能冒充其他用户。退款还会校验操作人是套餐订单购买者，核销校验传入门店与券实例所属门店一致。审计表保留请求号、券实例、动作、操作人、结果和拒绝原因，用于解释“为什么这次重试没有再次核销”。

当前项目没有独立商户员工、门店角色或支付服务，因此“核销操作人属于商户”的 RBAC 仍是保留风险；本轮只保证 token 身份不被请求体伪造和券不能跨门店核销。

## 4. 开发中的真实问题

### 4.1 本机 Flyway 基线与 README 不一致

README 声明已有开发库已由 Flyway 接管并写入 `flyway_schema_history`，但本机 `hmdp` 查询发现该表不存在。直接启动 Flyway 可能错误尝试执行历史 AI 迁移，因此本轮没有把“启动成功”当作迁移验证。`V30__voucher_package_fulfillment.sql` 作为正式增量文件保留；本机受控验证仅手动执行该文件创建三张全新的隔离表，未改动 `tb_voucher_order` 或旧券数据。

后续应先修复基线治理，再让新环境通过 Flyway 自动执行 V30；不能将本机手工执行冒充为完整迁移治理。

### 4.2 幂等审计抢占首次失败

第一次实现为了先抢占 `requestId`，在查询券实例之前插入了 `PROCESSING` 审计行。但审计表 `certificate_id` 是非空字段，真实接口实验的核销、退款和并发请求全部返回“服务器异常”，且券状态保持 `UNUSED`。这不是理论推断，而是本机接口实验实际发现的问题。

修复为：先只读按券码定位券实例，再插入带 `certificate_id` 的 `PROCESSING` 审计行，最后执行状态 CAS。失败在事务内回滚，不会留下无归属的处理中审计。

### 4.3 可重复读快照不能用于失败详情

核销和退款并发时，失败方在 CAS 影响行数为 0 后再查询券状态；MySQL 默认可重复读下该事务可能仍看到先前读取的 `UNUSED` 快照，即使另一事务已提交 `USED`。因此失败详情不能写成“当前状态为 UNUSED”。修复后统一记录“券状态已被其他履约操作改变”，避免日志和 API 对排障人员造成错误引导。

### 4.4 误核销撤销必须把时限写进 CAS

若仅在 Java 中判断 `used_time` 是否在 60 分钟内，再执行 `USED -> UNUSED` 更新，核销记录可能恰好在两条语句之间越过时限，或被另一请求改变状态。实现因此同时使用：

1. Java 预检查，快速返回明确原因；
2. 数据库条件更新：`WHERE id = ? AND status = 'USED' AND used_time >= ?`；
3. 成功后写入独立 `CANCEL_VERIFY` 审计记录并重新聚合套餐订单状态。

因此全量核销的单券套餐在成功撤销后会回到 `PAID`，部分核销套餐则回到与剩余券实例一致的聚合状态。撤销后券重新变为 `UNUSED`，可再次核销或在未使用前退款；这是纠正店员误扫的履约回滚，而非资金退款。

### 4.5 幂等回放必须校验业务语义

原先唯一索引只保证同一个 `requestId` 不会插入两次，但服务会无条件回放该请求号对应的审计结果。于是客户端错误地将一个已用于核销的请求号再用于退款，退款接口可能返回旧的“核销成功”；数据不会重复变更，却会让调用方拿到错误语义。

修复后，回放必须同时匹配 `requestId`、`action`、`certificateId` 与 `operatorId`。四者完全一致才是网络超时后的同一次重试；任一项不同都返回“请求号已用于其他履约操作，请使用新的请求号”。唯一索引仍负责并发抢占，语义校验负责阻止错误回放。取舍是请求号不能在不同动作之间复用，这符合以一次业务意图生成一个请求号的接口契约。

### 4.6 不同券并发会覆盖父订单聚合状态

代码审查发现，原 `refreshOrderStatus()` 在每张券状态 CAS 后，使用普通查询统计券状态，再无条件更新父订单。两张不同券并发操作时，券行锁不冲突：两个事务可能各自统计到“我这一张已变更、另一张仍是旧状态”的快照，再依次更新同一父订单。

以两张未使用券同时核销为例，两个事务都可能计算出 `PARTIALLY_USED`；后写入的旧计算会覆盖父订单，尽管两张券最终都已经是 `USED`。父订单行上的 `UPDATE` 锁只能把写操作排队，不能让等待方重新执行先前的普通快照统计。

修复后的统一顺序为：

1. 先按主键执行 `SELECT ... FOR UPDATE` 锁住 `tb_voucher_package_order`；
2. 再按 `package_order_id` 执行 `SELECT ... FOR UPDATE` 锁住并以当前读取得该订单全部券实例；
3. 对目标券执行原有状态 CAS，并同步更新内存中的锁定券集合；
4. 只从这批锁定的当前券状态聚合并更新父订单。

核销、退款、撤销核销均走同一锁顺序。InnoDB 的锁定读使用当前记录，而普通 `SELECT` 是一致性快照读；因此第二个等待父订单锁的事务在获得锁后会重新取得第一个事务已提交的全部券状态，而不是用旧快照聚合。[MySQL InnoDB 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

本机验证库实际查询 `@@transaction_isolation` 为 `REPEATABLE-READ`，所以不能把“后来加了父订单锁”误认为普通统计会自动刷新；正因如此，修复明确使用全部券实例的锁定当前读。

取舍是同一套餐的并发履约被短暂串行化，吞吐不再按券实例线性扩展；这是有意的，因为 `order_status` 是该套餐的派生一致性数据。不同套餐订单仍使用不同主键行锁，可并发执行。这里不使用 Redis 锁：最终状态和聚合数据均在 MySQL，数据库行锁与事务回滚能把状态迁移及聚合放在同一原子边界内。事务保持为少量 SQL，且所有路径先锁父订单再锁子券，减少死锁概率。[MySQL 死锁建议](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html)

## 5. 自动化与真实验证

自动化单元测试 `VoucherPackageStatusTest` 覆盖订单聚合状态：全未使用、部分使用、部分退款、全使用、全退款，以及不可能的计数。执行：

```bash
mvn -q -Dtest=VoucherPackageStatusTest test
```

`VoucherVerificationCancellationPolicyTest` 覆盖 60 分钟边界、窗口内、窗口外和空核销时间。两组单测可一起执行：

```bash
mvn -q -Dtest=VoucherPackageStatusTest,VoucherVerificationCancellationPolicyTest test
```

`VoucherFulfillmentIdempotencyTest` 覆盖同一次重试允许回放，以及跨动作、跨券、跨操作人的请求号复用被拒绝。完整执行：

```bash
mvn -q -Dtest=VoucherPackageStatusTest,VoucherVerificationCancellationPolicyTest,VoucherFulfillmentIdempotencyTest test
```

`VoucherPackageAggregationTest` 覆盖从同一套餐全部锁定券状态聚合最终订单状态，特别是“两张均已核销必须为 `USED`”，而不是错误保留为 `PARTIALLY_USED`。完整执行：

```bash
mvn -q -Dtest=VoucherPackageStatusTest,VoucherPackageAggregationTest,VoucherVerificationCancellationPolicyTest,VoucherFulfillmentIdempotencyTest test
```

本机真实接口实验使用 1 笔 3 张券的测试套餐订单，用户 `20260820001`，门店 `1`。顺序核销第 1 张、退款第 2 张；第 3 张同时发起核销与退款。

| 券实例 | 动作结果 | 最终状态 |
| --- | --- | --- |
| 第 1 张 | 核销成功 | `USED` |
| 第 2 张 | 退款成功 | `REFUNDED` |
| 第 3 张 | 核销成功；并发退款被拒绝 | `USED` |
| 整笔套餐订单 | 聚合结果 | `PARTIALLY_USED` |

审计流水记录了 3 条成功、1 条拒绝；拒绝动作没有改变券状态。这个实验说明 CAS 保住了单券互斥，但它不是支付渠道、Redis 故障、应用进程在事务提交后响应前崩溃等生产级覆盖。

同一张已核销券随后使用完全相同的 `requestId` 再次提交核销：接口回放第一条成功审计，数据库中该 `request_id` 的审计行数仍为 `1`，券状态仍为 `USED`。这覆盖了“服务端已提交、但客户端因网络超时重试”的最小幂等场景。

撤销闭环在同一台本机的隔离套餐券表中额外验证了两组场景：

| 场景 | 接口结果 | 数据库结果 |
| --- | --- | --- |
| 刚核销的单券套餐撤销，再用相同请求号重试 | 两次均成功，第二次回放 | 券 `USED -> UNUSED`，订单 `USED -> PAID`，`CANCEL_VERIFY` 审计仅 1 条 |
| 将另一张已核销测试券的 `used_time` 回拨为 61 分钟前后撤销 | 返回“仅支持撤销 60 分钟内的已核销券” | 券保持 `USED`，拒绝原因写入审计 |

第二组的时间回拨仅用于本地故障构造，不是线上运维操作。它验证了窗口外请求不会依赖客户端时间，也不会把已过结算窗口的券回退。该验证覆盖接口、数据库 CAS、订单聚合和审计；尚不是支付、结算或多机容量测试。

还对已成功撤销的券，故意复用其 `CANCEL_VERIFY` 请求号调用退款接口。接口返回“请求号已用于其他履约操作，请使用新的请求号”；数据库确认券仍是 `UNUSED`，没有新增 `REFUND` 审计。这验证了请求号保护的是同一业务意图，而不是只保护数据库不重复写。

### 5.1 JMeter 同券并发基线

新增 `jmeter/voucher-fulfillment-verify-race.jmx`。它使用同步定时器让 20 个线程同时以不同 `requestId` 核销同一张新建测试券；结果文件写在已忽略的 `jmeter/results/`。2026-08-20 本机结果：20 个请求、脚本错误率 `0%`、平均 `250ms`、最大 `274ms`、吞吐 `59.5 req/s`。

这些 HTTP 指标不能直接称为“核销成功 20 次”。压测后直接查询 MySQL，结果为 `VERIFY/SUCCESS=1`、`VERIFY/REJECTED=19`、券最终状态 `USED`。这说明同一券的数据库 CAS 在该受控单机并发下只允许一次状态迁移，其他请求被审计为拒绝。局限是它只覆盖单应用实例、单 MySQL、单张券、20 个请求的争抢正确性，不是容量上限、跨机故障或生产 SLA。

### 5.2 双 JVM 部署边界验证

单 JVM 的结论还不能证明实现没有暗中依赖本地内存。新增 `jmeter/run-voucher-fulfillment-dual-instance.sh`，在两台共享同一个 Redis/MySQL 的本地 JVM 上，对同一张新券各发 10 个不同请求号。启动实例的端口为 `8083`、`8084`，脚本执行：

```bash
bash jmeter/run-voucher-fulfillment-dual-instance.sh VC替换为新建测试券码 测试登录token
```

判定标准仍是 MySQL：20 个 `VERIFY` 审计中必须恰好 1 条成功、19 条拒绝，券最终为 `USED`。双 JVM 对这里有意义，因为它验证状态裁决确实落在共享数据库的 CAS，而不是依赖 JVM 内锁；但它不等于多机压测、故障转移或数据库高可用验证。

2026-08-20 实测启动 JVM A `:8083`、JVM B `:8084`，两者使用同一个本机 Redis/MySQL；脚本向两端各发 10 次请求。MySQL 查询结果为 `USED / SUCCESS=1 / REJECTED=19 / TOTAL=20`。两端请求均完成，且不存在重复成功核销。这是部署边界的正确性证据，不应延伸为多可用区、高可用或容量结论。

### 5.3 双 JVM 不同券并发聚合回归

新增 `jmeter/run-voucher-package-aggregation-dual-instance.sh`，令 JVM A `:8083`、JVM B `:8084` 分别核销同一套餐中的两张不同测试券。2026-08-21 本机实测后，MySQL 查询为 `order_status=USED / used_count=2 / certificate_count=2 / verify_success=2`。

这个场景与“同券只能核销一次”不同：两次核销都应成功，关键断言是父订单不能停留在 `PARTIALLY_USED`。结果证明锁后当前读与聚合逻辑在两 JVM、共享 MySQL/Redis 的受控环境下得到正确最终状态。它仍不覆盖 MySQL 主从延迟、进程在提交前后崩溃、连接超时重试风暴或支付结算。

## 6. 已完成与保留风险

已完成：套餐订单与券实例拆分；部分核销；仅未使用券退款；60 分钟内同门店误核销撤销；跨门店核销/撤销拒绝；购买人退款校验；请求号幂等及跨操作复用防护；核销/退款/撤销并发互斥；父订单锁加锁定券当前读的聚合一致性；审计流水；单元测试；20 线程 JMeter 同券争抢基线；双 JVM 同券争抢与不同券聚合的数据库业务正确性核验。

保留风险：真实支付退款、过期自动退款、结算后的人工售后、商户员工权限、动态券码、防刷、结算账本、Flyway 基线修复、容量压测和外部支付回调均未实现。本轮是可靠 MVP，不能表述为生产级资金或支付保证。
