# 商铺缓存 L1 与并发合并可靠性开发记录

## 1. 背景与现象

商铺详情接口原先只读取 Redis，再在 Redis 未命中时读取 MySQL。对普通请求这已经足够，但热门商铺的 Redis 缓存在同一时刻失效时，同一 JVM 内的大量请求会同时访问 Redis；如果 Redis 同时未命中，会继续形成 MySQL 回源峰值。这类短瞬间并发通常称为缓存击穿或缓存风暴。

原项目虽保留了逻辑过期实验代码，但生产读路径实际使用的是普通 Redis 穿透缓存；逻辑过期实验还使用固定线程池和无条件删除 Redis 锁，不能作为这次性能结论的基础。

## 2. 从发现到结果的完整故事

### 2.1 先确认问题是否真实存在

沿着 `ShopServiceImpl#queryById` 的实际调用路径排查后，确认线上读路径是 Redis 穿透缓存：Redis 未命中就查询 MySQL。它没有把同一 key 的并发请求合并起来。原代码中虽有逻辑过期示例，但该示例并非当前读路径，且使用固定线程池和无条件释放 Redis 锁；直接拿它作为“已经解决热点缓存问题”的依据并不成立。

因此，本次要验证的不是“缓存能不能命中”，而是一个更具体的问题：**热点商铺进入刷新窗口时，单个 JVM 内的并发请求会不会把 Redis L2 打成突发峰值，以及这个峰值能否被可测量地压缩。**

### 2.2 排查中发现的环境风险

在接入测试和本机压测时，默认 `selectById` 因实体中的地区字段与本机 `tb_shop` 缺列而失败。继续检查发现，本机 `hmdp` 没有 `flyway_schema_history`，且表结构仍是旧的手工初始化版本。这不是缓存本身的故障，却会让“缓存回源 MySQL”无法可靠验证。

本次没有为了通过压测直接修改本机业务库或强行执行全部迁移：数据库没有迁移历史时，Flyway 无法判断哪些脚本已在旧库中以手工方式执行，直接迁移可能重复建表、执行演示数据写入或改变已有数据。压测运行时明确关闭 Flyway，并在缓存读路径使用只查询当前旧表实际存在列的 `ShopMapper#selectCacheById`。这是**兼容性止血**，不是“本地数据库已同步到最新 schema”；数据库基线梳理应作为独立、先备份再演练的可靠性闭环。

### 2.3 方案为何这样选

候选方案是手写 `ConcurrentHashMap + CompletableFuture` 的 SingleFlight，或复用 Caffeine 的异步加载缓存。后者对同 key 返回同一个加载 future，已包含并发合并能力，少一套取消、异常映射和竞争清理代码，且可同时提供最大容量、刷新窗口、命中统计。

所以最终采用“Caffeine L1 异步刷新 + Redis L2 + MySQL”的小范围改造：热点读取优先返回仍有效的旧值，只有一个刷新任务访问 Redis；首次加载失败时删除失败 future，避免客户端重试持续复用错误结果；更新事务提交后再失效 L2 与本机 L1，避免事务回滚却提前清缓存。

### 2.4 结果如何证明

先用 `ShopLocalCacheTest` 构造 1,000 个 JDK 21 虚拟线程同时访问一个 key，断言 Redis L2 仅被读取一次；再验证首次加载异常后可以立即重试，以及显式失效后能够读到 L2 新值。随后在真实本机 Redis、MySQL 和 JMeter 下，以 200 个同步释放的同 key 请求做开关对照，记录 HTTP 错误、P95/P99、L2 与 MySQL 回源计数。

结果是：L1 关闭时，压测阶段产生 200 次 Redis L2 加载；L1 开启后，压测阶段只产生 1 次合并刷新（脚本另有 1 次预热），P95 从 69ms 降至 39.9ms，P99 从 75ms 降至 46ms，两个组的业务错误率均为 0%。这证明了单实例刷新窗口内的削峰效果；它不证明跨实例一致性、Redis 故障下的可用性或生产容量，剩余边界见第 8 节。

## 3. 目标与边界

本次只优化 `GET /shop/{id}` 的读路径：

```text
浏览器请求 -> Caffeine L1（当前 JVM） -> Redis L2 -> MySQL
```

- MySQL 仍是事实源；Redis 仍是共享缓存。
- L1 只保护一个 JVM。多实例部署时，最多做到每个实例一次回源，不能说成全局只回源一次。
- 不将评论、秒杀、AI 状态机等业务接入本次改造。
- 不通过清 Redis、清库或伪造延迟制造压测结果。

## 4. 方案

`ShopLocalCache` 使用 Caffeine `AsyncLoadingCache`。同一个 key 的首次加载值是同一个 `CompletableFuture`，并发请求会等待并共享该 future，而不是自行维护 `ConcurrentHashMap`。

默认参数：

| 参数 | 默认值 | 原因 |
| --- | ---: | --- |
| L1 开关 | `true` | 可通过 `SHOP_CACHE_L1_ENABLED=false` 关闭，作为压测对照组。 |
| 最大条目数 | 5,000 | 防止进程内缓存无限增长。 |
| 刷新窗口 | 5 秒 | 热点请求到来时异步刷新。 |
| 硬过期 | 30 秒 | Redis 或数据库长期故障时不无限期保留旧值。 |
| 刷新线程池 | 2 核、最多 4、队列 100 | 限制刷新工作对业务线程的影响。 |

热点 key 到达 5 秒刷新窗口后，调用方仍优先得到旧值；只有一个异步任务读取 Redis L2。与硬 TTL 后让所有请求同步等待相比，这个策略主要稳定请求延迟，并降低 Redis 突发回源量。

商铺更新事务提交后，先删除 Redis L2，再失效本机 L1。若 Redis 删除失败，仍失效本机 L1 并记录结构化警告；这会留下最长 Redis TTL 的跨实例旧值风险，不能表述为强一致性。

## 5. 失败处理

首次异步加载失败时，调用方按错误返回，且会按 future 身份删除失败映射。这样网络瞬时错误不会让紧随其后的客户端重试继续复用失败 future。

刷新旧值失败时，Caffeine 保留已有旧值，下一次访问可再次触发刷新；因此“有旧值的热点刷新失败”和“第一次无缓存加载失败”是两种不同场景。

## 6. 自动化验证

`ShopLocalCacheTest` 覆盖：

1. 1,000 个 JDK 21 虚拟线程同时读取同一商铺，断言 Redis L2 `get` 仅调用一次。
2. 第一次 MySQL 加载抛异常后，下一次请求能重新加载成功。
3. L1 命中旧值后显式失效，下一次请求读取 L2 的新值。

执行：

```bash
mvn -q -Dtest=ShopLocalCacheTest test
```

## 7. JMeter 受控压测

脚本为 `jmeter/shop-cache-singleflight.jmx`。它先用一个请求预热，再等待 6 秒进入 L1 刷新窗口，最后用 Synchronizing Timer 同步释放同 key 请求。

先分别启动两个实例，不能同时使用同一个端口：

```bash
# 对照组：关闭 L1
SHOP_CACHE_L1_ENABLED=false mvn -q spring-boot:run

# 实验组：启用 L1（默认）
mvn -q spring-boot:run
```

每个实例启动后，先读取并保存初始统计，再执行：

```bash
~/Downloads/apache-jmeter-5.6.3/bin/jmeter -n \
  -t jmeter/shop-cache-singleflight.jmx \
  -l jmeter/results/shop-cache-l1-enabled.jtl \
  -e -o jmeter/results/shop-cache-l1-enabled-report \
  -Jthreads=200 -JrampUpSeconds=1 -JshopId=1

curl -s http://127.0.0.1:8081/internal/cache/shop/stats
```

对照组使用相同参数，将结果名改为 `shop-cache-l1-disabled`。`jmeter/results/` 已被 Git 忽略，保存真实 `.jtl` 和 HTML 报告，不提交机器相关产物。

必须同时记录：HTTP 错误率、吞吐、P95/P99、`l2LoadCount`、`databaseLoadCount`、Caffeine 命中率、加载失败数。启用 L1 后，在单实例的这次刷新窗口中，突发请求对应的 L2 增量应接近 1；若不是，应先检查脚本是否确实等待了刷新窗口、是否命中同一实例和同一商铺。

### 2026-08-18 本机受控结果

环境为单个 Spring Boot 实例、MySQL 9.7、Redis 本机实例、JMeter 5.6.3，商铺 ID 为 `1`，主突发组 `200` 线程、`1` 次循环。两组均先预热 Redis L2，再等待 6 秒；数据库没有在压测期间写入或清理数据。

| 指标（仅 200 个突发请求） | L1 关闭 | L1 开启 | 说明 |
| --- | ---: | ---: | --- |
| HTTP 错误率 | 0% | 0% | 两组均返回业务成功。 |
| 平均响应时间 | 50.6ms | 12.4ms | 单机本地结果，不外推为线上容量。 |
| P95 | 69ms | 39.9ms | JMeter HTML 报告的 95 百分位。 |
| P99 | 75ms | 46ms | JMeter HTML 报告的 99 百分位。 |
| L2 加载次数 | 201 | 2 | 关闭组为 1 次预热 + 200 次突发；开启组为 1 次预热 + 1 次进入刷新窗口后的合并刷新。 |
| MySQL 加载次数 | 0 | 0（压测阶段） | 两组前均已有 Redis L2 数据；本实验隔离的是对 Redis 的突发回源。 |

开启 L1 的实例统计为 `hitCount=200`、`missCount=2`、`loadFailureCount=0`、`l2LoadCount=3`。其中第一笔 L2 加载发生在 JMeter 前的接口可用性检查，因此 JMeter 阶段的 L2 增量为 2。关闭 L1 后 Caffeine 不参与调用，其命中率字段没有解释意义，不能拿它与开启组比较。

结果文件已保存在本机被 Git 忽略的 `jmeter/results/`：`shop-cache-l1-enabled.jtl`、`shop-cache-l1-disabled.jtl` 及对应 HTML 报告。吞吐在两组间没有显著提升，这是因为 200 请求在极短突发内完成，瓶颈不是 CPU；本次结论是“回源压缩与延迟改善”，不是“最大吞吐翻倍”。

## 8. 取舍与剩余风险

- 不使用自研 SingleFlight：Caffeine 已提供 future 合并，少维护异常清理、取消和竞争条件。
- 不只用硬 TTL：硬失效只能合并回源，不能保证等待请求的 P99；逻辑刷新允许热点请求读旧值。
- 不替换 Redis：L1 重启即丢失，不能承担共享状态或分布式一致性。
- 没有跨实例失效广播：当前通过更新后删除 Redis 与短 L1 TTL 限制陈旧窗口。多实例且更严格的一致性需求出现时，可复用 Redis 做失效通知，但需要额外验证消息丢失和重连。
- Redis、MySQL 同时不可用时，首次读取仍会失败；本次不引入无限期本地兜底，避免返回不可控的陈旧商铺数据。

## 9. 面试表达

“我把商铺详情改成 L1 Caffeine、L2 Redis、MySQL 事实源的三层读路径。L1 使用异步刷新和同 key future 合并，热点 key 刷新时只允许一个请求回源，其余请求复用旧值或同一个 future。压测除了看 HTTP 延迟，还核对 L2 回源计数、缓存命中率和错误率。这个优化是单 JVM 的削峰手段，不宣称跨实例全局只回源一次；更新后仍以 Redis 删除和有限 TTL 控制一致性窗口。”
