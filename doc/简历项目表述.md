# 消费决策 Agent - 简历项目表述

## 一句话介绍

面向本地餐饮消费场景的多轮决策 Agent。通过会话状态、地理位置槽位、结构化商户检索、评价证据与工具调用，完成“提出需求 - 澄清位置/约束 - 推荐 - 评价/优惠/营业时间追问”的可审计闭环。

## 简历条目

- 基于 Java 21、Spring Boot 3.4、Spring AI、MySQL、Redis、Milvus 构建餐饮消费决策 Agent；实现闲聊与餐饮任务动态路由、显式退出和自然重入，避免非餐饮需求误触发推荐链路。
- 设计服务端 `ConversationState`：将活动决策、最近决策、位置授权状态、行政区和候选商户焦点持久化到 MySQL，并以 Redis 缓存最近聊天记忆；解决多轮对话中位置重复索取、指代丢失和跨城市候选串联问题。
- 构建“硬过滤 + 语义重排”的 RAG 链路：MySQL 先按行政区、半径、预算、菜系和营业时间过滤，Milvus 仅在候选白名单内做评价/画像语义召回；加入相似度阈值与证据覆盖率，保证向量检索不突破业务约束。
- 基于 Spring AI `ToolCallback` 适配商户详情、评价证据、优惠券和备选商户工具；记录工具参数、执行状态、结果摘要与耗时，并对已展示候选的指代进行服务端解析与强制绑定。
- 建立单轮检索评测和多轮对话轨迹评测：覆盖 Recall@K、MRR、证据覆盖率、硬约束违规、工具覆盖率、路由/本地性/最终状态命中、Token 与延迟；支持主评测集、留出集、版本对比和失败案例诊断。
- 引入 Flyway 管理后续数据库增量迁移，并使用 JMeter 对完整 AI 决策路径进行受控并发压测；4 并发、8 次真实请求下错误率为 0%，P95 为 5.02s。

## 可量化数据

- `vector-v3` 检索主评测：15 条用例，Recall@K `0.8333`、MRR `0.5833`、证据覆盖率 `1.0`、硬约束违规 `0`、模型调用成功 `29/29`、P95 `5.77s`。
- 多轮对话主评测：10 条轨迹，路由、本地性和商户命中均为 `10/10`，必要工具覆盖 `6/7`；未通过的状态用例保留为候选数据不足或放宽策略的待优化项。
- JMeter 受控并发：4 线程、10 秒 ramp-up、每线程 2 次，8/8 HTTP 成功，平均 `4.34s`、P95 `5.02s`。

## 面试讲解顺序

1. 先说明这是有明确业务边界的餐饮 Agent，而不是泛聊天机器人：推荐必须来自本地事实数据和证据。
2. 说明多轮难点在状态而非单次提示词：聊天历史、位置槽位、当前/最近决策、候选商户焦点分别由不同的服务端实体承担。
3. 说明检索策略：硬条件用于召回边界，向量用于候选排序；先保证不跨城、不超预算、不违背菜系，再追求语义相关性。
4. 说明工具调用安全性：模型负责规划，服务端负责 schema 校验、候选绑定、执行和审计；不让模型直接决定事实结果。
5. 最后展示评测与压测：用留出集和失败诊断定位回归，用真实模型端到端压测观察延迟、错误率和成本边界。

## 不应夸大的表述

- 不应称为“生产级高并发系统”；当前压测是受控并发基线，瓶颈包含上游模型调用。
- 不应将 `LOCAL_DEMO` 评价和商户数据表述为真实大众点评线上数据。
- 不应说已完成通用 MCP 生态或全自动 Agent；当前 MCP 用于地点解析，核心工具循环保留服务端业务控制。
