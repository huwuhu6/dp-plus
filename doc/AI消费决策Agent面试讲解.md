# AI 消费决策 Agent 面试讲解

## 一句话定位

这是一个面向本地消费选择的受控 Agent：模型负责把自然语言转成约束，后端负责事实、状态机、检索、重排和评测。目标不是让模型自由编故事，而是在模型波动、缺少信息或没有候选时，仍能给出可解释、可恢复、可验证的结果。

## 一条请求如何完成

1. 用户输入“附近 100 米内的寿司，不想排队”之类的自然语言。
2. DeepSeek Tool Call 提取菜系、预算、距离、时间、场景等结构化约束；失败时走本地规则。
3. 后端合并 HTTP 坐标等确定事实，并补足“女朋友/男朋友/情侣”为约会场景等可确定含义。
4. 以预算、距离、营业时间和菜系做硬过滤；场景、安静和排队风险做确定性重排。
5. 缺坐标进入 `CLARIFYING`；无候选进入 `WAITING_RELAXATION`，只能由用户选定放宽项后继续。
6. 最终店名、价格、距离、营业时间和证据都由后端拼接，模型不拥有事实字段的最终表达权。

## 为什么这样设计

### 模型不生成最终推荐文案

真实调用中模型曾把正确店名复述错。现在模型只做约束提取，最终答案使用数据库中的事实字段和证据模板生成。这降低了幻觉风险，也减少了一次无效模型调用。

### 不自动放宽条件

没有坐标时猜位置、无候选时偷偷扩大距离，都会改变用户意图。系统暂停并展示受控选项，用户确认后才恢复；恢复使用条件更新保证同一暂停会话只有一个请求可以继续执行。

### 暂不接向量数据库或 Spring AI

原项目没有足够真实评论，先接向量库只能得到“技术栈存在、检索证据不足”的演示。当前先建立结构化画像、可引用证据和固定评测基线。后续有真实评论与更大标注集后，再在 Java 17/Spring Boot 3 升级分支比较关键词、向量和混合检索的 Recall、MRR、延迟与成本。

| 14 | holdout-v1 | 状态/约束 4/4，续聊 1/1，模型成功 4/4，P95 4476ms | 收尾版本的独立保留集最终基线 |

运行 13 和 14 都达到 Recall@K/MRR/证据覆盖率 `1.0`、硬约束违例 `0`、事实一致性全命中。当前评测持续记录状态命中、约束命中、Recall@K、MRR、证据覆盖、事实一致性、硬约束违例、模型成功/失败率、平均总耗时和 P95。

## 一个可讲的 trade-off

运行 8 平均总耗时比运行 7 快 544ms，但 P95 慢 1053ms。运行 11 在质量全对时 P95 进一步达到 16724ms。结论不是“系统很快”，而是：数据库筛选和重排开销很小，主要等待来自模型约束提取；平均值改善不代表最慢用户的体验改善。

因此当前选择是保留规则降级和受控状态机，优先保证正确性和可恢复性。模型提取失败时，接口会返回 `degradedReason`，明确说明已由本地规则继续处理；这比悄悄给出结果更利于用户判断和线上排障。更细的重试、熔断和限流属于后续生产化工作。

## 已知边界

- 商户画像和证据中有 `LOCAL_DEMO`，不能称为真实用户评论。
- 开发集 15 条、保留集 4 条，适合演示回归，不代表线上统计显著性。
- `RUNNING` 评测可由创建者主动终止；线上应再加入任务心跳和自动回收。
- 当前没有真实用户点击、收藏或转化反馈，因此不能训练个性化排序模型。

## 候选追问

**为什么不用纯 Prompt？**

因为距离、预算和营业时间是可验证事实，应该由后端约束，不应该依赖模型“记住”。

**如何证明修复有效？**

每次策略变更会写入检索版本，用同一模型、同一数据集和同一用例规模比较；例如 v2 将约束命中从 14/15 提升到 15/15。

**如果模型失败怎么办？**

记录失败次数并走本地规则，接口会返回 `degradedReason`。运行 7 证明降级路径也会出错，因此加入了米单位解析测试和保留集验证，而不是假设降级天然可靠。
