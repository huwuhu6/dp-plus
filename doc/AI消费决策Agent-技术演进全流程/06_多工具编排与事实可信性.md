# 多工具编排与事实可信性：从商户追问到V2有界执行

> **事实范围**：8月V1 Tool Orchestration历史开发记录 + 当前main的ToolExecutionOrchestrator、V2ActionHandler、MerchantFactObservation、V2ResponseRenderer与10月实际受控模型对照。V1旧Pipeline不等于当前V2默认执行主链。历史数字均注明评测类型。

## 1. 这个问题为什么不是让模型多调用几次工具就行

~~~text
用户：“第一家评价怎么样，还有优惠券吗？”
~~~

如果模型只挑search_shop_evidence，回答了评价却遗漏优惠券，整体语义不完整；如果让模型随意猜优惠券，容易编出并不存在的商品规则。正确的执行要求是：同一商户身份、两个独立只读事实、两个真实工具结果、一个不会丢掉任一事实的最终回复。

再看更复杂的一句：“第二家不辣就去”。它不仅需要读取商户对应主餐的辣度证据，还必须根据本轮已证实的事实决定是否执行选店，并确保POST选择真正提交成功，然后才能回复“已选”；“工具返回了一个答案”不等于“业务效果已经落库”。

## 2. V1：工具共享可变Context时出现的隐式状态机

最初BaseAgentTool曾接收可变AgentSessionContext：get_shop_detail可改变焦点商户，search_alternative_shops可直接改变已展示集合。这样只要多个工具的调用顺序改变，就可能出现不同结果；工具一边读一边写，令并发、安全回放和测试难以推断。

8月25日引入独立ToolStateDelta：工具输入先在编排层从Working Memory物化，工具只输出业务事实及声明的状态差异；归约器集中按顺序提交，避免每个工具自行持久化。这是从“工具隐式修改上下文”向“工具是相对纯函数，Reducer负责写状态”迁移的关键。这个V1过渡构件对理解V2很重要，但不应写成目前V2主链还逐节点调用原V1 Pipeline。

## 3. 并行不等于无序：哪些工具能够并行

历史ToolExecutionOrchestrator区分PARALLEL_SAFE与有状态动作：
- get_shop_detail、query_shop_vouchers、search_shop_evidence、compare_shops属于基于既定对象的只读查询，可以在独立上下文快照中并行；
- search_alternative_shops会影响候选/展示等状态，不能直接与读取焦点的工具无序竞争，历史方案将其串行；
- 模型计划最多读取三项只读工具调用；若明确“评价+优惠券”只生成一项，针对受控复合事实语义可由Java补足已知缺项；
- 按原计划顺序聚合，而不是按最快返回顺序修改焦点。

真实代码中仍可定位并行执行、独立snapshot、completeOnTimeout、有限工具超时等机制：[ToolExecutionOrchestrator.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/ToolExecutionOrchestrator.java)。这类基础服务代码存在，并不能证明每个V2 ToolAction都走该编排器；当前V2直接由V2ActionHandler绑定只读工具，需要按Action链区分。

早期定向代码测试：两条各350ms的只读工具在600ms内并发完成。**这不是线上吞吐指标**。8月25日真实conversation-v1 Run22（14条轨迹）路由、工具断言、最终状态14/14，必要工具覆盖10/10，平均11707ms。真实复合事实回放同时调用search_shop_evidence(shopId=25)和query_shop_vouchers(shopId=25)；不能推广为全部组合问题均正确。

### 为什么要限制工具结果大小

评价文本、券规则及商品JSON可能非常长。把全部结果塞进后续模型Prompt会增加Token和截断风险。ToolResultCompressor把displayText限制在1600字符、单文本240字符、列表最多6项、事实项最多12项；历史开发记录中的摘要240字符预算与当前实现需分别检查，不应认为所有早期常量都未改变。

压缩必须服务“让模型看得下”，不能抹掉用于后续事实裁决的唯一证据；涉及价格、商品属性、同店身份时优先保留类型化事实源而不是自由文本概括。

[ToolResultCompressor.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/tool/ToolResultCompressor.java)。

## 4. V2：从“Tool调用列表”升级为有依赖和Guard的执行动作

V2中先解释UserRequest（FactQueryRequest、SelectRequest、RecommendationRequest等），Grounding把“第二家”绑定真实shopId，Compiler形成ExecutionAction与ExecutionPlan。ActionExecutor/V2ActionHandler将事实类型映射到存在的只读业务能力：

- VOUCHER→query_shop_vouchers；
- EVIDENCE/REVIEW/QUEUE→search_shop_evidence；
- PRICE/PRODUCT读取已绑定商户的确定性事实，返回类型化Observation；
- NON_SPICY_MAIN_MEAL需要同店主餐辣度来源，作为后续选择Guard的前提。

支持的执行模式是有界DAG；当前部分CompareAction/GeneralAnswerAction明确UNSUPPORTED，不是宣称任意多Agent推理都能自动完成。

**一个关键差别**：执行观察可以是KNOWN、UNKNOWN或技术异常；未知不是“否”。例如“无骨的吗？”若没有可靠菜单提供者，答案必须明确“目前无法确认”，不能因为商户详情里缺少该字段就断言“没有无骨”。

当前MerchantFactObservation记录shopId、FactType、原文question、KNOWN/UNKNOWN与source。PRICE只有与绑定shopId一致、平均价格为正且具有来源的事实才能形成可靠答复；PRODUCT需同店同属性的证据匹配。LLM不能直接用常识生成商户商品存在性。

源码：[V2ActionHandler](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/V2ActionHandler.java)、[MerchantFactObservation](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/MerchantFactObservation.java)。

## 5. “第二家不辣就去”：事实、选择与最终文案必须在同一轮闭环

~~~mermaid
flowchart TD
 U[用户: 第二家不辣就去] --> G[Grounding识别当前Batch第二家]
 G --> T[Fact Tool读取同店辣度证据]
 T --> P{证据是否满足Guard}
 P -->|是| S[执行Select/产生效果]
 P -->|否/未知| N[不执行选择]
 S --> O[POST提交selectedShopId]
 O --> R[Renderer同时告知事实+本轮已选店]
 N --> R2[明确证据不足, 不冒称选择完成]
~~~

旧Bug C23：事实和POST选择已成立，但最终回答只讲食材，没有确认选择。修复后V2ResponseRenderer可同时保留factAnswer、recommendations及本轮selected效果，且不读取旧selected值冒充本轮刚选。**选中仅指系统当前Task状态，绝不等于餐厅已收到预订或完成下单。**

## 6. 如何识别“业务真实通过”与“只读工具返回正常”

成功必须分层：
1. 模型正确表达事实请求种类；
2. Grounding绑定对的Task、Batch、shopId；
3. Action实际调用对应只读事实能力，而非按店名猜数据；
4. 事实确有来源；缺字段时UNKNOWN而非false；
5. 条件性动作满足Guard才产生DomainEffect；
6. POST实际写入成功，Renderer准确承接事实、推荐和本轮业务效果。

Run201的24/24不能覆盖所有事实主题；16场景受控验收仍有真实菜单、楼层、接待能力和地理事实缺口。**局部S02/S06/C23的闭环是可验证的，未验证场景不写成成功**。

> 【核心提炼】从V1工具共享可变Context到V2强类型Action/Observation，最重要的不是“并行更多工具”，而是把商户身份、事实来源和执行后状态效果分开：模型可以提出要查什么，商户身份靠历史Batch，事实由工具给出，状态只有Reducer/OCC能修改。
