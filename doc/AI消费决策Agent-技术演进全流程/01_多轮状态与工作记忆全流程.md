# 多轮状态与 Working Memory：从分散槽位到 Task Scope、版本化状态和 V2 双阶段提交

> **阅读目标**：读完能沿真实用户语句解释每一次状态从哪来、属于哪个Task、为何能/不能改变、保存在哪、并发时怎样避免覆盖。本文优先解释业务现场和数据流，再标注代码。  
> **版本边界**：V1历史实现从开发记录和Git提交还原；“当前”仅指main（821422d）。Task V2（9月初的历史命名）≠9月14日切换主链的Agent V2。

## 1. 真正的困难不是“多保存几条聊天”

从最容易复现的一组对话讲起：

~~~text
用户：福州附近找火锅，人均100元以内。
Agent：给了三家火锅店，记为 Batch A。
用户：换到杭州找日料，预算300。
Agent：给了另一批日料店，记为 Batch B。
用户：还是最开始福州火锅吧，不过预算改80。
~~~

最后一句不是“把当前杭州日料里的菜系改成火锅，预算设80”，而是“恢复第一套福州方案并只改其中预算”。如果程序只有一份 currentCriteria，那么第二轮必然覆盖福州、火锅、100。第三轮需要模型从聊天历史反推先前状态，可能恢复菜系却留下杭州或300元。这种“看上去有上下文，但业务状态不确定”的失败，是Task Scope出现的直接原因。

这里先区分：
- Chat History：用户和助手说过的文本，用来帮助语言理解，可能截断、摘要、不完整。
- Working Memory：当前已确认、可以让SQL与工具执行的业务状态，是结构化可读写事实，不靠每轮LLM重建。
- Task：同一chat中的一套独立消费方案，例如福州火锅A、杭州日料B。
- RecommendationBatch：某一次实际展示给用户的一组**有序**候选；它支持“上一批第二家”这种历史身份表达。
- PlanningSnapshot：当前V2某一轮完成PRE提交后冻结的执行依据，不能在慢工具运行中途悄悄换成更新后的世界。
- Runtime Event：记录一次语义解释、策略决定或工具结果怎么发生，服务审计；不等于最新业务状态。

这些概念不是同义词，生命周期和写入者不同。最初的错误正是把临时聊天状态和长期决策事实揉到一起。

## 2. 第一阶段：聊天、会话槽位与单次Decision的执行上下文

### 2.1 历史当时的数据散在哪里

8月16—24日前，位置槽位放在会话表（当时的slots_json），候选商户、焦点店、条件快照保存在某次decision session的agent_context_json，本轮临时Context又保存原话、改写句、路由结果、当前候选等。单个模块能读到需要的信息，但没有一份跨轮公认的业务事实源。

~~~mermaid
flowchart LR
  A[历史chat消息] --> C[当前请求临时Context]
  B[会话位置slots_json] --> C
  D[某次decision的agent_context_json] --> C
  C --> E[模型/规则解释本轮]
  E --> F[执行并回写若干状态]
~~~

为什么早期这样可用？普通“推荐 → 问第一家价格”主要需要候选序号和焦点店；只要上一轮结果留在当前decision里就够。为什么后面不够？新推荐决策的产生会换掉执行会话，旧条件未必自动继承；即使引用能解析，系统也不知道“这轮没提到预算”究竟是继续保留还是清除。

### 2.2 第一个修复：引入统一Working Memory

8月24日新增 ConversationWorkingMemory 和对应迁移V32，把设备/目标位置、当前筛选条件、候选池、焦点商户、对话阶段与决策会话关联集中起来。这解决的不是Token问题，而是读写一致性：后续请求不再用“重新理解整个历史”代替取出当前条件。

当时双写旧slots_json服务迁移兼容，是历史过渡措施。后来的V40把主记忆转为 tbl_ai_working_memory 版本快照；不能把V32下写会话行的方案描述成当前存储模式。

代码证据：[32daa32f](https://github.com/huwuhu6/dp-plus/commit/32daa32f)、[V32](https://github.com/huwuhu6/dp-plus/blob/main/src/main/resources/db/migration/V32__chat_session_working_memory.sql)、[ConversationWorkingMemory.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/dto/ConversationWorkingMemory.java)。

## 3. 第二阶段：previous + delta，让旧条件稳定而不是每轮重建

例子：第一轮“福州附近、川菜、人均200、3km”；第二轮“不要辣的，换粤菜”。第二轮用户没说“仍在福州”“预算仍是200”“半径仍是3km”，但这几个值不应该被清空。正确操作是继承地理范围、预算和距离，只替换菜系并加入清淡偏好。

历史ConversationCriteriaMerger把本轮变化归为：
- inherited：用户未提，旧值保持。
- replaced：用户明确给了新标量（如粤菜替换川菜）。
- appended：标签或偏好集合去重追加。
- cleared：用户明确表示“不限预算”“不用安静”“不要原来菜系”。

为什么需要区分“没有”和“删除”？因为稀疏提取的budget=null没有足够信息判断“本轮未谈预算”还是“用户说预算不限”。因此后来明确引入clearedFields/removedPreferences等操作信号，而不是简单拿新对象覆盖旧对象。

这时产生新的错误：**约束更新了，候选还没更新。** 如果上一轮是川菜店A/B/C，本轮变粤菜，用户再说“第二家呢”，程序可能仍从过时的川菜候选读取商户。仅有Merger返回新条件仍然不够，必须在状态归约时联动使旧“当前可见候选”与焦点失效。

~~~text
V1旧候选 A/B/C（川菜）
  ↓ 用户“换成粤菜”
Merger 得出 cuisine=粤菜
  ↓ 若不级联失效
candidatePool仍是 A/B/C，focusedShop仍可能是川菜
  ↓ 后续事实工具引用旧对象
发生语义与数据对象不一致
~~~

于是增加 State Reducer：条件变化后确定性失效候选、焦点，记录CASCADE_INVALIDATED原因及旧候选数量，再交给搜索生成新快照。地理位置变更也会让候选域失效。最初的“清空候选”针对当前投影，不代表必须删除作为历史事实的所有批次；后续Task Scope采用RecommendationBatch长期保留可回溯身份。

真实验证：Run9的条件细化回放中预算200、半径3km保留、菜系换成粤菜，但本地严格检索无符合商户，进入WAITING_RELAXATION；Run14在12条集合里工具断言12/12，Run12对应10/12。不过中间并非单一变量改动，不能把整个差额算成Reducer收益。后续修改评测预期，将严格零结果等待授权认作正确安全边界，不应为了更高“完成率”放宽条件。

证据：[39ecba3f](https://github.com/huwuhu6/dp-plus/commit/39ecba3f)、[042546aa](https://github.com/huwuhu6/dp-plus/commit/042546aa)、[开发记录8月24日](https://github.com/huwuhu6/dp-plus/blob/main/doc/AI消费决策Agent开发记录.md)。

> 【核心提炼】状态变更不仅要修改字段，还要处理依赖旧字段生成的派生状态；“历史曾经推荐过什么”与“当前这轮仍允许用什么”不是同一个概念。

## 4. 第三阶段：Memory Version + Runtime Event，把状态提交变成有资格的操作

### 4.1 并发覆盖如何真实发生

假设两个终端同时查看chat版本V20：
- 请求A根据V20把预算改80；
- 请求B根据V20把Task切到杭州。

没有版本资格校验时，两个请求各自在完整内存快照上改值，再覆盖写同一行。B最后写入可能丢掉A的80元变更。这不是LLM是否准确的问题，是典型Lost Update。

8月26日V40迁移建立 tbl_ai_working_memory，一次写入追加新的version和完整memoryJson；(chat_id,version)唯一索引防止两个请求抢同一版本。WorkingMemoryVersionService.append读取latest，比较expectedVersion，若不同抛 VersionConflictException；相同则尝试写version+1。若两个请求恰好同时通过读取比较，数据库唯一键把第二个插入拦下来。

~~~java
AiWorkingMemory current = latest(chatId);
int actualVersion = current == null ? 0 : current.getVersion();
if (actualVersion != expectedVersion) {
    throw new VersionConflictException(chatId, expectedVersion, actualVersion, operationType);
}
row.setVersion(expectedVersion + 1);
workingMemoryMapper.insert(row);
~~~

这几行体现**数据写入资格**：基于V20理解得到的决策不能在V21已经出现后无条件落库。不是凭空说“乐观锁更快”——项目没有同chat三档并发吞吐或冲突率对照数据。

### 4.2 为什么版本冲突不能直接重放旧对象

假设B在旧Task上形成“第二家预算改80”，请求A先切换到另一个Task并保存V21。如果B发现冲突以后只是读取V21，再把原来计算好的对象硬覆盖上去，极可能把B的旧候选身份套到新Task。正确重试至少需要重新判断任务归属、实体引用和其他因果输入，否则应拒绝并要求客户端重试。这是Agent状态与普通“数据库字段+1”的关键区别。

历史V1偏保守拒绝旧结果；当前V2不是“永远不重试”，而是：
- PRE冲突：重新读取并重新解析Task/Grounding，最多两次尝试。
- POST冲突：读取最新版本，确认原Task仍有效；若因果输入未变可复用同次执行观察，若改变则基于最新Snapshot重新编译和执行一次；再次冲突则返回可重试响应。
- 候选产生后的响应要等POST提交获胜才能对用户呈现为正式结果。

关键源码：[WorkingMemoryVersionService.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/WorkingMemoryVersionService.java)、[V2ChatOrchestrator.java第78—99/176—203行](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/V2ChatOrchestrator.java)。

### 4.3 为什么事件要与业务状态分离

一次完整Agent轮次可能记录 USER_INPUT、SEMANTIC_INTERPRETATION、工具调用、检索、结果校验、最后回答，但其中绝大部分不是用户业务事实的持久化修改。Runtime Event回答“发生了什么”，Working Memory回答“当前是什么”。状态发生变更时在同一事务写version和关联STATE_REDUCED Event；普通非状态事件用于诊断，不应每条生成一份memory快照。

V1曾记录Rewrite、Route等链路事件；V2运行事件结构演进以后，不可机械假定所有旧事件类型仍以相同位置产生。这里描述的是持久化契约，不是宣称可观测性指标完整——Run201/202的模型聚合计量仍有旧session ID缺失导致的漏记。

### 4.4 请求幂等不同于OCC

OCC的键在chat+version，防“多个不同业务修改”的覆盖；幂等键最终由userId+chatId+scope+idempotencyKey组合，防“同一个客户端命令重发”被重复执行。IdempotencyService还校验SHA-256 requestHash，重复成功请求重放resultJson，重复处理中拒绝，key相同但请求不同报冲突；没key则不承诺重试幂等。这两者不能合并宣传为一把通用分布式锁。

## 5. 第四阶段：A→B→A，为什么必须有Task级记忆

### 5.1 旧模型无法同时表达两套方案

全局activeCriteria只有一个组合：
~~~text
A：福州 / 火锅 / 人均100
B：杭州 / 日料 / 人均300
回到A：如果只能在B上改字段，就必须从历史猜出A的所有条件
~~~

Task模型改为：
~~~text
ConversationWorkingMemory
  activeTaskId: "task-A"
  tasks:
    task-A: 福州/火锅/预算100/推荐批次A1,A2
    task-B: 杭州/日料/预算300/推荐批次B1
  deviceLocation: 设备所在位置（整个chat共享，不因换Task改变）
  focusedShopId: 当前对话聚焦商户
~~~

用户明确回A后应从已有Task A读出“福州、火锅、100”，仅把其中预算改为80；Task B继续保持杭州日料300。这个模型解决的不是“历史查找速度”，而是状态归属。Task是业务方案身份，Version是时间演进，两者维度正交：V20与V21都可以同时包含Task A和B，只是当前活动Task或其中字段发生了变化。

### 5.2 第一版Task V2为何仍没解决问题：同轮双快照

这是仓库里非常具体的开发事故，不该一句“修复状态不一致”略过：
1. 请求起点读取Memory A。
2. Pipeline前半程在内存里新建或切换到Task B。
3. 后半程reduceCriteria又从MySQL读取一次旧版本。
4. 由于前面的修改尚未持久化，第二次查询看到的是仍以Task A为活动任务的旧世界。
5. 用旧快照继续归并和保存，第一次正确的Task切换被覆盖。

解决：在同一轮内存归约链只使用一份权威Memory，不在节点之间重新取旧DB快照。历史定向Task Scope四条：Flat State Run85=2/4；Task第一版Run87=2/4；修复后Run89/90=4/4。同阶段Run89完整多轮鲁棒性7/24，说明**局部修复成功不等于整体Agent已正确**。

证据：[472da9da](https://github.com/huwuhu6/dp-plus/commit/472da9da)、[da5b06bd](https://github.com/huwuhu6/dp-plus/commit/da5b06bd)、[历史开发故事01](https://github.com/huwuhu6/dp-plus/blob/docs/interview-prep/doc/01_多轮对话状态与工作记忆——开发故事与面试准备.md)。

### 5.3 Task边界也是产品语义

“换到杭州找日料”显然开新方案；“预算改80”通常只是当前方案内更新；“还是火锅吧”可能表示在杭州继续找火锅，也可能表示恢复之前福州火锅，光有菜系词不够恢复旧城市。V1曾有地点+菜系签名等启发式创建/恢复规则，可能少拆或误拆Task。

V2通过TurnSemantics.taskDirective（CONTINUE、START_NEW、RESTORE、ABANDON）及taskDirectiveEvidence，结合EffectiveTaskContextResolver的历史Task绑定，再由TaskLifecycleReducer真正决定持久化操作。对于模糊历史Task引用，返回澄清而不是假定某个任务。**事实查询旧商户不授权自动恢复整个旧Task**：可以从历史Task读取候选绑定shopId，但不能因此把旧城市、旧预算整体覆盖当前活动Task。

代码路径：[TurnSemantics](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/semantic/TurnSemantics.java)、[EffectiveTaskContextResolver](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/grounding/EffectiveTaskContextResolver.java)、[V2ChatOrchestrator.preparePre](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/V2ChatOrchestrator.java)。

## 6. 第五阶段：推荐历史到底保存什么，为什么不能只存candidatePool

一旦用户说“第二家”，光有列表[A,B,C]或集合{A,B,C,D,E,F}不够。下一轮可能先看第二批[D,E,F]，再问“最开始第二家”。程序必须知道B来自**第一批的第二个位置**，E来自**第二批的第二个位置**。于是使用RecommendationBatch，每批保存有序RecommendationCandidateRef，包括shopId、shopName等必要引用事实。

~~~text
Task A：
 Batch A1：11,22,33
 Batch A2：44,55
用户：“上一批第二家”  → 任务下最新可见批次A2 / shopId=55
用户：“最开始第二家”  → 根据明确历史选择器 / 批次A1 / shopId=22
~~~

上面11/22/33与44/55是仓库受控Fixture里使用过的商户标识，用来帮助理解映射机制；并不表示当前真实福州生产数据库的商户列表。

保存Batch以后，shownShopIds可以是历史批次集合派生的查询视图；excludeShopIds是本次搜索策略参数：用户“换一批别重复”确实适合排除近期店，用户“还是上一批那个店”则不该重新搜索后又把目标店排除。不能让“曾经展示过的全部店”无限期自动加入任何搜索排除集。V1文档已记录过过粗的全部历史排除规则；V2引入更强类型的请求与拒绝集合，但**本次没有独立全面验证任意换批表达下的产品策略**。

### 6.1 已解决与尚未解决的规模问题

ChatMemoryService提供的最近聊天消息上限，不代表数据库Working Memory无限增长问题已解决。Task可能越来越多，每个Task的Batch可能越来越多；Memory又按每次业务变更保存完整JSON快照。

若第k轮状态大小近似随k线性增长，累计k个完整快照的理论体积近似1+2+…+k，即O(k²)级别。这是存储模型的风险推导，**没有生产容量事故实测证据**。当前main没有已验证的Task/Batch统一热窗口裁剪、冷历史归档、旧Memory版本TTL或增量快照压缩。后续如做在线窗口，必须保障“最开始第二家”超出窗口时澄清或查询冷历史，不能把被裁剪后第一条现存批次冒充原始第一批。

## 7. 第六阶段：V2如何把Memory操作分成PRE与POST

V1常把抽取、状态修改、执行和持久化放在贯通的Pipeline中；若本轮有条件分支，就不容易区分哪些条件现在就有效，哪些需要等SearchObservation才能变成事实。

V2的一轮分成：
1. 语义解释得到TurnSemantics。此时不应直接写入长期状态。
2. 读取最新版ConversationWorkingMemory、解析Task与商户引用；旧反馈可能属于旧Task，新需求属于新Task，两者在本轮PRE按确定性归属处理。
3. PreExecutionReducer只归约可直接确定的普通CriteriaPatch、RelativePreference、RelaxationAuthorization、RequirementLock、已明确绑定的反馈；ConditionalRequirementChange在PRE被跳过。
4. PRE通过WorkingMemoryVersionService.append提交，获得新version；由这份已提交的Task构建PlanningSnapshot。
5. 编译/执行/验证；产生SearchObservation、Tool结果和DomainEffect。
6. PostExecutionReducer仅按允许的效果修改状态、更新选中商户与实际推荐批次。
7. POST再次OCC提交。若因果上下文已变化，按受限重试策略重新编译/执行或返回重试响应。
8. 只有提交成功的候选结果才作为正式结果交给Renderer。

~~~mermaid
flowchart TD
  A[读最新Memory/解析用户本轮] --> B[Task身份和实体Grounding]
  B --> C[PRE Reducer: 确定用户事实]
  C --> D[PRE expectedVersion + 唯一键提交]
  D --> E[PlanningSnapshot冻结]
  E --> F[Compiler + Executor]
  F --> G[Verifier过滤硬约束]
  G --> H[POST Reducer应用执行效果]
  H --> I[POST OCC提交]
  I --> J[Render + appendTurn]
  H -.冲突.-> K[重读/判断因果输入/有限重算]
  K --> I
~~~

这里的两次OCC不是两次无条件重复写相同字段：PRE把用户已授权的新状态正式确立，POST把执行后才知道的事实合入已提交的世界。如果POST失败，不能冒称工具结果已经进入当前记忆。

**重要边界**：这套架构确立了“条件分支由POST提交”的分工，但不自动保证所有条件分支语义都正确。最新代码已知requiresCuisineCoverage把备用菜系当作主约束覆盖，且备用搜索EMPTY仍可能触发ConditionalCriteriaApplied。关于这两个不同问题参见02与04篇，不应在本章写“条件污染已彻底解决”。

## 8. 三类回到以前，不是一种操作

1. **Task切换**：当前最新版Working Memory里并存A和B，更新activeTaskId指向A；不改变历史数据库版本。
2. **历史只读**：load_history等入口读取旧version，为用户解释发生过什么；不会自动把它写回当前状态。是否仍被当前V2主链直接使用，应按对应调用路径判断，不能拿旧工具存在当作主链常用。
3. **恢复历史版本**：读取旧完整业务状态、做权限与冲突校验，并把它作为新的最大version提交，例如现有V30、恢复V12内容后形成V31；不是把数据库指针倒回V12。

这三种操作的共同安全约束：不能因为读到了某个旧对象，就默认拥有把整个旧状态覆盖当前状态的权限。

## 9. 当前主要取舍与剩余边界

| 设计 | 带来的确定性 | 成本与局限 |
|---|---|---|
| 持久Working Memory | 不必每轮重建全部条件 | Task和批次持久化增长、数据模型维护 |
| Task隔离 | A/B多方案可以同时保存 | 开新Task/续旧Task/切回旧Task的语义边界仍有歧义 |
| 有序Batch | 跨轮、跨批次商户身份可确定 | 热状态历史窗口尚未治理 |
| 全量版本快照 | 审计、历史读取、CAS冲突保护 | 重复存储增长 |
| PRE/POST独立OCC | 用户事实和执行后效果的提交资格分离 | 冲突时要判断因果输入，可能需要重新执行工具 |
| 有界冲突重试 | 避免无限重试及旧结果乱写 | 在高并发下可能返回请重试，缺真实压力与冲突率对照 |
