# 结构化约束与单轮语义：从“每轮重新猜”到强类型、分阶段提交

> 当前源码基准：main 821422d。本文重建V1→V2演进，不把历史的DecisionConstraints与当前DiningCriteria混为一谈。技术问题围绕“用户说了什么、到底要改什么、改哪个Task、什么时候可以落库”展开。

## 1. 用户说了“日料”，未必代表要修改菜系

~~~text
第1轮：在附近找川菜，人均100以内。
第2轮：第一家那个日本料理环境怎么样？
~~~

第2轮提到“日本料理”可能只是用来描述历史商户，不意味着用户要求将正在生效的筛选条件从川菜改成日料。类似地，“第二家人均多少？”里的“人均”是查询店铺事实，不是设置用户预算。**出现某个词（mention）和要求修改对应状态（mutation）是两种语义。**

如果让“约束提取器识别到字段”直接触发写Working Memory，下轮推荐就可能被一次事实追问污染。这条主线不是“多加几个Prompt例子”，而是逐渐将**语义解释、授权写入、作用域选择、实际提交**拆开。

## 2. 起点：单轮结构化抽取，模型输出并非用户事实的最终权威

最初由ConstraintExtractor将开放中文转换成DecisionConstraints（地点、菜系、预算、半径、偏好等）；Java执行硬过滤。常见输入：“福州附近人均100以内的日料”。

至少有三类误差：
1. 用户实际请求的设备坐标可能在HTTP参数里，不在自然语言文本里；模型输出不能擅自替代设备事实。
2. 菜品名称可能包含地名，如“重庆鸡公煲”“西安肉夹馍”；模型将内嵌地名误读成搜索城市，直接造成错误SQL范围。
3. 多轮时模型未必每次输出所有旧字段；如果直接用“本轮完整对象”覆盖，之前的预算、地点、菜系会丢失。

8月30日ConstraintExtractor v1/v2 Prompt实体边界实验：Baseline原记录16/17→17/17；Holdout维持7/8（87.5%），其中“搜索西安肉夹馍店”仍误抽西安。这是特定独立实验，不意味着后续V2对任意地名都正确。开发记录还指出规则式菜系canonicalization要双侧统一，避免“用户侧寿司→日料、商户侧没同样归一化”出现不对称过滤。

## 3. V1第一次演进：上一轮已确认的字段必须继承

前提：
~~~text
Memory有效条件：福州、川菜、人均200、3km。
新话语：不要辣，换成粤菜，继续找。
~~~
如果再生成“完整条件”，本轮没有再次提预算/距离，模型很可能省略。V1改用previous + sparse delta：仅提本轮明确变化，再通过ConversationCriteriaMerger应用。

### 3.1 四种合并动作和固定先后关系

| 操作 | 场景 | 处理语义 |
|---|---|---|
| 继承 inherited | 本轮没有谈预算 | 保留之前的200 |
| 替换 replaced | 换成粤菜 | cuisine从川菜改成粤菜 |
| 追加 appended | 再加“安静” | 去重追加偏好 |
| 清除 cleared | 预算不限 / 不用安静 | 删除明确指定字段/偏好，不删其他值 |

为何不是“新字段不为null就覆盖”？因为null既可能是“未提及”，也可能是“明确取消”。为此先用V1模型的clearedFields、removedPreferences等标记；清除与写新值次序固定，防止“不要川菜，改粤菜”先写后清而把新值也删掉。

8月24日真实Run9测试条件细化，预算200、3km继承与粤菜替换均有记录，但因为数据没有符合条件的店，进入WAITING_RELAXATION。该结果说明保持约束而不是偷偷放宽，不能写成已找到合适商户。

证据：[32daa32f](https://github.com/huwuhu6/dp-plus/commit/32daa32f)。

### 3.2 新问题：改了值，但之前的候选仍然属于旧条件

上一轮川菜A/B/C可以用于“第二家怎么样”；本轮已经切到粤菜后，如果当前候选仍然指向A/B/C，则模型/工具仍可能读出川菜。State Reducer根据变更维度使旧候选与焦点失效，同时保留历史批次用作只读事实。**条件归约与候选派生状态失效必须是一条事务语义**。

证据：[39ecba3f](https://github.com/huwuhu6/dp-plus/commit/39ecba3f)、[042546aa](https://github.com/huwuhu6/dp-plus/commit/042546aa)。

## 4. V1第二轮修补：明确取消、相对反馈、硬条件锁定

### 4.1 “看看别的吃的”为什么不能继续继承沙县

历史问题：上一轮限定沙县，查询无店；用户说“看看有没有别的吃的”，字面上没有提供新的菜系值，但在语境中表达的是**放弃旧菜系约束**。如果简单认为“cuisine=null=没提”，系统继续把沙县留在当前条件，可能反复得到空结果。

后续clearedFields允许本轮明确“清除cuisine/keyword”，而不是一味继承旧字段。案例标识是“沙县”用户反悔；不是“任何自然语言反悔都被完美识别”。

证据：[81d8ace4](https://github.com/huwuhu6/dp-plus/commit/81d8ace4)、[77846543](https://github.com/huwuhu6/dp-plus/commit/77846543)。

### 4.2 “第二家太贵了”：先知道第二家是谁，才能决定降到多少

这里必须分清两个动作：
1. 识别商户引用。历史推荐Batch按顺序存真实shopId；“第二家”绑定当前可见批次第二个，不能由LLM猜ID。
2. 识别RelativePreference。本轮用户要求相对变便宜，而不是绝对输入预算。V1使用被指向的商户价格作为优先锚点，找不到明确商户时回退焦点/候选；历史曾用锚点×0.85取整并设20元下限（例如165×0.85≈140）。

为什么不是简单“预算-1”？缺乏商业意义；为什么0.85不是最优？它只是经验参数，没有同条件长期用户反馈A/B证明。

相对反馈还引出一类逆向bug：用户说“太贵了”，系统降低预算后严格零结果，却仍展示“提高预算”放宽按钮，相当于绕过用户刚表达的更便宜要求。因此引入锁定条件，禁止没有新授权就反向放宽。历史V1里存在预算锁定及方向脉冲清理；V2改为typed RelativePreference和Lock/RelaxationAuthorization，不能继续把V1定值算法说成V2目前保存的原始用户条件。

### 4.3 写权限门槛为何从字段抽取中分开

V1通过Routing/CriteriaIntent先决定本轮是否允许合并Delta，再调用ConstraintExtractor。优点是事实追问的“人均”“日料”不能自动改长期状态；代价是静态规则过窄时可能错过复杂表达。

旧资料中的 hasExplicitMutationSignal 等逻辑解释的是**V1的门控位置**。V2已不再依赖固定旧Pipeline完成该控制，而是把用户请求、条件变更、任务操作表示为统一TurnSemantics，再由确定性Reducer只处理确切允许的类型。强类型并不保证模型永不错误：来源校验可能漏判，也可能误拒绝。

## 5. 商户实体引用为什么是约束问题的一部分

~~~text
Batch1：[11,22,33]
Batch2：[44,55]
用户：“最开始第二家人均多少？另外当前那家太贵了。”
~~~

这里含两个不同对象：历史第一批的第二个=22；“当前那家”需按当前批次、聚焦商户等语义解析。如果模型只输出一个“shopId=22”又在后续Rewrite里重新理解“那家”，就可能把价格查询与预算反馈都绑定到22，造成事实和状态双重错误。

V1使用ReferenceIntentExtractor（规则+模型识别中文指代），BatchAwareReferenceResolver按历史批次确定shopId；原话中的start/end用于校验文本位置，不允许把模型输出的数组下标直接当真实身份。真实店是谁应由保存的推荐事实决定，而不是一次模型猜测决定。

V1固定Rewrite可能再次把shopId改写回中文后让Router二次理解。“当前位置，除了东北菜都可以”若被Rewrite成“按当前位置找”而丢掉排除东北菜，就是语义信息经过多层自然语言改写而变质的真实风险。于是原话保留为语义证据，Rewrite只能作为帮助。

9月7日历史引入TurnCommandSet/TurnUnderstandingService收拢单轮语义判断，随后9月14日V2进一步以TurnSemantics+Grounding替代V1各节点分别理解。V2还区分只读历史商户事实与真正恢复历史Task：**可以查询历史22号店，但不能因为读到了旧店便切换整套旧预算和城市。**

证据：[474d4830](https://github.com/huwuhu6/dp-plus/commit/474d4830)、[V2 GroundingResolver](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/grounding/GroundingResolver.java)。

## 6. V2强类型语义：不再让DecisionConstraints兼任所有角色

旧DecisionConstraints可以同时承担“最终有效条件”“模型本轮Delta”“辅助操作”“系统推导策略”——简单但很容易把暂时意图当成长期事实。

V2拆成：

| 对象 | 存什么 | 是否可以直接修改长期Memory |
|---|---|---|
| TurnSemantics | taskDirective / evidence、requirementChanges、entityFeedback、requests、relations、references | 否。它是本轮语义提议 |
| DiningCriteria | location、cuisine、budget、distance、diningTime、preferences、partySize、dietaryRestrictions | 是Task规范的用户条件，但修改只能经Reducer |
| RequirementChange.CriteriaPatch | 本轮明确设置或清除的条件 | 满足来源与任务边界后由PRE应用 |
| RequirementChange.RelativePreference | 相对于已有候选或要求的价格/距离变化 | 保存为相对信号，不冒充用户指定数值 |
| RequirementChange.RelaxationAuthorization | 哪个维度允许放宽 | 进入允许集合 |
| RequirementChange.RequirementLock | 哪个维度不得反向放宽 | 进入锁定集合 |
| RequirementChange.ConditionalRequirementChange | “满足某观察才改条件”的候选效果 | PRE忽略；POST按执行效果处理 |
| GroundedTurn | 已绑定Task、历史Batch和商户实体的可执行语义 | 不能绕过Reducer直接写状态 |

### 6.1 一轮PRE如何执行

1. SemanticInterpreter读取用户原话得到TurnSemantics，不代表已经落库。
2. Working Memory读取最新版本，EffectiveTaskContextResolver确定本轮Task归属或需要澄清。
3. GroundingResolver把“第一批第二家”“当前商户”映射到历史真实shopId与批次，不直接接受模型虚构ID。
4. TaskLifecycleReducer处理START_NEW/RESTORE/ABANDON/CONTINUE。
5. PreExecutionReducer将普通CriteriaPatch、相对偏好、锁定/授权以及已Grounded的反馈归约到V2TaskState。
6. V2LocationResolver校验本轮执行地理锚点；不能确定时返回澄清，不捏造坐标。
7. WorkingMemoryVersionService.append尝试PRE OCC提交。只有成功之后形成PlanningSnapshot，供下游计划执行。

### 6.2 ConditionalRequirementChange：为什么“没有火锅就烧烤”不可提前提交

~~~text
用户：如果3公里内没有藏式火锅，就改找烧烤。
确定主条件：藏式火锅，半径3km。
待执行分支：仅当主搜索观察结果EMPTY，才尝试烧烤。
~~~

如果普通抽取器把两个菜系简单写成 cuisineAnyOf=[藏式火锅,烧烤]，主搜索一开始就可以返回烧烤，完全违背“先找藏式火锅，没有再改找”的执行顺序。

V2 PreExecutionReducer代码把ConditionalRequirementChange列为忽略项：它还不是已确认要持久化的用户条件。Compiler据此构建有依赖与Guard的有界DAG：主搜索→EMPTY条件判断→备用搜索→依赖执行效果。PostExecutionReducer只读取真正发出的DomainEffect并应用CriteriaPatch。

~~~java
case RequirementChange.ConditionalRequirementChange ignored -> {
    /* external observation decides whether it may become durable */
}
~~~

此代码来自[PreExecutionReducer.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/reducer/PreExecutionReducer.java)。它证明PRE不会**直接处理这个类型**，不能证明前面模型校验不会先把备用菜系转成普通CriteriaPatch，也不能证明备用搜索本身EMPTY后不会提交效果。

~~~mermaid
flowchart TD
  U[原话: 没有藏式火锅就烧烤] --> S[TurnSemantics: 主约束+ConditionalChange]
  S --> PRE[PRE只保存确定的主约束]
  PRE --> A[SearchAction 藏式火锅]
  A -->|非EMPTY| N[不执行备用]
  A -->|EMPTY| B[SearchAction 烧烤]
  B --> E[EmitDomainEffect]
  E --> POST[POST应用ConditionalCriteriaApplied]
~~~

## 7. V2来源校验：为什么确定性规则也能把正确的模型结果改坏

### 7.1 2026-10-15真实反例：FIRST正确、后处理错误

两个正式评测都涉及：“如果3公里内没有藏式火锅，就改找烧烤”。模型FIRST提取到主菜系藏式火锅、3km、备用烧烤的正确分工。随后SemanticInterpreter.requiresCuisineCoverage调用CuisineCanonicalizer.requestedCategories(userTurn)，对**整句**检出藏式火锅和烧烤，却只在普通CriteriaPatch里统计已覆盖菜系，误触发CUISINE_COVERAGE_REQUIRED。

Main的定向修复把备用烧烤加入根cuisineAnyOf=[藏式火锅,烧烤]，因为现有Main断言只检查分支个数/距离，没有检查根菜系是否被提前污染，仍被记为24/24通过。

Semantic另一条运行把单值cuisine=藏式火锅与OR并列输出，parser认定互斥，整轮失败。这不是模型FIRST不理解条件句，是确定性覆盖验证忽略了条件分支的作用域。它属于**已有真实Run202失败加源码归因**。

源码：[SemanticInterpreter.requiresCuisineCoverage](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/SemanticInterpreter.java)、[统一评测第116—125行](https://github.com/huwuhu6/dp-plus/blob/main/doc/eval/DineWise-V2-统一评测与优化对比.md)。

### 7.2 第二个独立边界：备用搜索EMPTY仍可能发出提交效果

ExecutionPlanCompiler为备用SearchAction设了主搜索EMPTY的Guard，但后面的EmitDomainEffectAction只依赖备用group成功结束，没有再次校验备用搜索是否查到候选。StaticPlanExecutor视EMPTY为非技术失败；因此备用搜索组EMPTY仍可能被标为正常完成，执行DomainEffect。V2ActionHandler返回SUCCESS效果观察，PostExecutionReducer据此应用ConditionalCriteriaApplied。

**证据等级：代码调用链审计；本篇没有新增五条独立运行复现。** 与7.1真实模型失败是两件事；只有业务规则要求“备用也为空不许持久化”时才构成该提交契约的缺陷。现有实验分支有隔离测试草案，不可视为已执行通过或已修复。

源码：[ExecutionPlanCompiler.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/plan/ExecutionPlanCompiler.java)、[StaticPlanExecutor.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/runtime/StaticPlanExecutor.java)、[PostExecutionReducer.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/v2/reducer/PostExecutionReducer.java)。

### 7.3 无依据字段、非法修复与来源边界

Semantic Run202另一失败SEM_CLEAR：“找人均100以内的火锅”竟把100填进distanceKm并生成无依据partySize，遗漏budget；REPAIR又新增无依据人数和不辣。来源校验拒绝，首轮零提交，后轮“预算不限”因为没有成功建立任务上下文而进入澄清。不能凭后轮行为断言Budget clear Reducer有bug。

阶段收尾S08出现“冷面或者寿司”被别名正则错误匹配成“面或者寿司”，误拒绝；C03则出现FIRST漏食材，定向修复补了食材却改写“不能吃太辣”的原文表述，字面来源校验拒绝。这些都说明：**即便把决策下沉Java，代码规则也要被独立评测，不能默认为绝对权威。**

## 8. 完整演进的几个取舍

| 决策 | 为什么这么做 | 仍有代价 |
|---|---|---|
| 每轮只提变化 | 防漏旧条件 | 区分“没提”与“清除”必须有操作类型 |
| 先决定写权限 | 防事实追问污染约束 | 规则过窄可能漏合法变更 |
| Grounding实体身份 | 真实shopId由Batch决定 | 多历史批次/复合引用需要明确Task和批次 |
| RelativePreference独立表示 | 不伪造用户直接说的绝对金额 | 执行时仍需可信锚点与策略 |
| 强类型RequirementChange | 不同修改行为具备不同提交语义 | Schema/模型修复器仍有复杂交叉验证 |
| PRE/POST分离 | 条件效果要等执行后才能确认 | 多一次OCC及因果冲突处理 |
| Fail closed来源验证 | 没证据不提交 | 可能出现正确语义被拒绝的false negative |
| 可追溯评测 | 发现“最终回复对但状态错” | 当前Main仍有覆盖不足的盲区 |
