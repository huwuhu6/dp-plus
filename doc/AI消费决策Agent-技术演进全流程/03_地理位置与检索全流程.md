# 地理位置与混合检索：可信位置、MySQL硬过滤、Milvus排序和索引修复

> 当前事实基准：main 821422d。历史V1字段、现行V2组件及实验指标分别标注；这是工程复盘，不是生产能力证明。

## 一、起因：同一个“附近”，为什么会搜错城市？

~~~text
设备在福州。
用户：帮我看看杭州西湖附近的日料，人均120以内。
~~~

设备位置是用户手机当前所在的地方；命名目的地是本次Task要搜索的范围。杭州西湖不能被福州GPS替代；“西湖”也不能直接充当district行政区字段。类似地，“重庆鸡公煲”里的重庆不是搜索城市，“福州大学”里的福州也不必然等于用户明确要求福州市全城搜索。

历史V1以targetProvince/City/District/Area、locationIntent、nearby/radiusKm表示位置；当前V2以DiningCriteria.LocationCriteria、SearchAnchor以及V2LocationResolver负责执行身份。不能把旧DTO名当作最新主链契约。

## 二、最初的三类位置表达与边界

- 行政区：省、市、区县，是有限层级实体，依赖父级身份，合法时参加行政硬过滤。
- POI：大学、商场、车站、地标，必须通过地图实体解析获取明确名称与经纬度，不能冒充区县。
- 设备坐标：仅在用户要查自己附近等允许的场景作为地理事实；切Task不能改变手机实际位置。

历史行政区解析采用本地Registry并结合上下文父级消歧，模型提供的行政候选不能绕过来源校验。“鼓楼”缺城市时可能存在多实体，partial registry只查出一条不能证实全国唯一。POI经地图服务返回候选，entityTypeHint等模型推断只能帮助排序，不能做硬过滤。地图不可用或身份不能确认时澄清，不凭空编坐标。

### 一次真实Prompt失败

8月30日实体边界实验：历史ConstraintExtractor Prompt v1→v2，对17条Baseline从16/17→17/17，8条Holdout仍7/8。“搜索西安肉夹馍店”仍错误抽出西安搜索城市。这个结果说明Prompt能改善已见类型，但不能证明全部地名表达已正确。

## 三、从地点槽位到V2执行锚点

V1将searchLocation作为Task的搜索目的地，deviceLocation作为chat设备事实。地点从福州切厦门时，旧区县/POI、焦点店与当前候选必须失效；不能再把先前城市商户当作当前候选，但历史RecommendationBatch应保留供明确历史引用。

当前V2的V2LocationResolver输入包含规范DiningCriteria、可选设备坐标、上一SearchAnchor和是否发生位置变更；输出Resolved(SearchAnchor)或NeedsClarification。执行前只有在必要的身份和坐标足够可靠时才允许走下游。当前实现区分城市/区县行政范围查询、POI唯一候选和距离半径依赖，存在按原SearchAnchor复用的受控路径。

~~~
用户说“西湖附近”
→ 提取poi及行政上下文
→ LocationResolutionProvider得到多个或唯一候选
→ 校验名称、城市、经纬度
→ 唯一合法时生成SearchAnchor
→ SearchSpec在这个锚点上计算地理限制
→ 若无法确认则澄清，而非偷偷回退到手机位置
~~~

最新V2代码会按当前设备、行政范围及用户指定地点组合不同搜索锚点：不能笼统声称“只要有命名城市就绝不读取设备坐标”；是否会被距离策略消费，要看SearchSpec具体字段。历史V1按“附近”默认3km，10月14日进一步区分用户明确的硬半径与系统默认扩大策略。

## 四、为什么不是全交给Milvus：硬过滤和语义排序各做什么

~~~text
硬约束：福州/火锅/预算<=100元/3km。
软偏好：安静、有氛围、适合约会。
~~~

真实检索分层：

1. TurnSemantics和DiningCriteria确定用户所要求的条件，Compiler产生SearchSpec。
2. MySQL商户与画像过滤合法性：行政、预算、菜系、距离等约束。**并非所有硬过滤都在SQL层完成**；一部分在画像或检索服务内二次检查。
3. 只有存在合法shopIds，才在Milvus使用allowed shop ID白名单预过滤，将Profile/Review文档语义相关性作为排序信号。
4. 文档分数按商户ID聚合；结合评分、距离、预算契合、语义分数等确定性重排。
5. DeterministicResultVerifier复查候选身份、预算、距离、菜系、排除集合及证据缺口；Renderer只使用已支持的事实。

~~~mermaid
flowchart TD
 A[本轮SearchSpec] --> B[MySQL与画像硬过滤]
 B --> C{合法商户是否存在}
 C -->|否| D[零结果，不向量凑数]
 C -->|是| E[Milvus allowed IDs白名单语义检索]
 E --> F[文档到商户MAX聚合]
 F --> G[确定性排序与Verifier]
 G --> H[展示/保存推荐批次]
~~~

历史上先检索整个Milvus再后过滤，合法候选占比低时TopK可能被不合法文档占满。后改为Milvus表达式预过滤；V2→V3索引文档数量、数据条件不同，不能将两者错误数差额当严格单变量收益。

## 五、35条同快照消融：真正证明了多少

历史检索消融：35条查询、112条GT商户。V_Base、V_Sem加权18、V_Sem_2x加权36采用同一次数据快照：

| 指标 | Base | Sem 18 | Sem 36 |
|---|---:|---:|---:|
| Recall@3 | 0.7291 | 0.7614 | 0.7722 |
| NDCG@3 | 0.9355 | 0.9558 | 0.9704 |
| Top1 | 0.9355 | 0.9355 | 0.9677 |
| 硬约束违反 | 0 | 0 | 0 |

18权重相对Base的Recall@3增加3.23个百分点，但Top1不变。它证明**在同组历史检索样本里语义得分对最终排序有贡献**；不能说Agent总体正确率提升，也不能说明36权重全局更优。

另一个独立tags A/B：同35条查询，content-only与content+tags的Recall@3均0.7932，Top1均0.9655；NDCG@3分别0.9828/0.9873。评价tags改变了文档相似度，但该组没有改变Top1和Recall@3。生产内容并未因为提出content-only方案而自动完成索引切换。

## 六、为什么有增量同步和索引对账

MySQL是Review和Profile等业务事实的权威存储；Milvus是用于近似语义检索的索引。MySQL评价已更新、Milvus仍是旧向量时会短暂不一致。不能把远程Embedding/Milvus写入绑进MySQL主事务并假设跨库原子。

当前使用持久化的tbl_ai_vector_sync_task：每个稳定document_id唯一记录最新目标revision与UPSERT/DELETE，状态PENDING→SYNCING→SYNCED。高revision覆盖旧revision，同revision删除优先；Worker用operation、revision、lease token领取和回写，网络失败退避重试，过期租约恢复。Milvus Writer采用稳定ID delete→add（不能把普通add默认为原子upsert）；MySQL已经提交的业务事实不会因为网络失败被回滚。

~~~mermaid
flowchart TD
 A[MySQL Review/Profile变更] --> B[同步事务中形成持久化任务]
 B --> C[Worker原子claim并持有lease]
 C --> D[Milvus稳定文档ID写入或删除]
 D -->|成功且版本仍匹配| E[SYNCED]
 D -->|失败/版本已变化| F[重新排队]
 G[Reconciliation比对期望和实际] -->|发现漂移| B
~~~

VectorIndexReconciliationService识别MISSING、STALE_REVISION、FINGERPRINT_MISMATCH、ORPHAN；只重新入队持久化同步意图，不直接写Milvus。Schema不兼容时停止。当前vector-sync定时Worker默认disabled，因此“已经实现代码”不代表“所有环境自动长期执行”。

[任务表V57](https://github.com/huwuhu6/dp-plus/blob/main/src/main/resources/db/migration/V57__ai_vector_sync_task.sql)；[VectorSyncWorker](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/VectorSyncWorker.java)；[对账Service](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/VectorIndexReconciliationService.java)。

## 七、当前客观限制与边界

- 2026-10-15福州330商户/330画像的审计中，面食、米线、酸菜鱼、炸鸡等细粒度画像匹配0；评论提及餐品不等于已核验当前菜单。真实首轮“福州三坊七巷找面馆、50元内”：MySQL候选经画像硬过滤后为0，Milvus未调用；这不是向量召回失败。
- 多城市同名POI、校区、楼宇、硬距离定位来源有复杂边界，缺证据须澄清。
- 没有可依赖的当前商户菜单、营业、可接待人数等完整事实时，Verifier不应声称全部业务要求得到满足。
- 没有本次的生产级增量同步延迟P95/失败率、全量对账耗时和真实商户世界稳定性数据。

> 【核心提炼】地点负责“在哪个可信空间搜”，MySQL/画像负责“哪些店合法”，Milvus负责“合法店中哪些语义更贴近”，排序与Verifier负责“以哪些可核验事实展示”，增量同步和对账负责“索引尽量跟得上真实业务数据”。任何一层都不能越权替代另一层。
