# 运行时可靠性与交付：模型失败、状态事件、幂等、SSE和降级

> **来源**：2026-08-15至10-15的仓库开发记录、V40/V53/V54迁移与当前main源码。历史V1服务与当前V2入口有所区别，不因代码存在便宣称全部在V2主链相同位置执行。没有重新执行压力测试。

## 一、为什么Agent“模型回答对了”仍然不代表请求成功

聊天Agent既要调用远端LLM、MySQL/Milvus、地图MCP和商户工具，也要把结果存到可恢复的会话里，并可能通过SSE交给浏览器。任意环节失败都可能造成**实际执行成功但网关超时、工具已运行但审计丢失、状态已变化但用户没收到响应、重复提交导致相同命令执行两次**。

因此运行时可靠性不应只写“增加重试和日志”，而要具体说明每种失败发生在什么边界、哪些事实已经持久化、允许重试哪一步、什么情况下必须停止。

## 二、最早的真实模型失败：超时配置写在配置文件里却没有实际生效

8月15日Run7（15条seed-v1）平均4584ms、P95 5915ms，模型仅成功8/15。排查发现两类问题：
1. HTTP客户端并未实际应用ai.timeout-ms=20000的连接和读取超时，配置只是字符串，并没有约束真实调用。
2. 模型失败后本地规则降级不能解析“附近100米”的“米”，漏掉0.1km硬距离，造成不符合用户原话的推荐。

修复后Run8模型15/15、平均4040ms、P95 6968ms。平均下降但尾延迟上涨，说明不能声称全面性能提升。后续对客户端失败和降级增加可观察的degradedReason；不要把“本地规则产出可读答案”统计为“LLM本次成功”。

### 10月14日的模型传输退避

某次S01失败不是一般用户Schema错误，服务端明确返回sandbox grammar compile timed out；SemanticInterpreter的REPAIR只解决结构化语义，不负责恢复供应商网络/服务能力。因此在OpenAiCompatibleClient增加受控重试：可配置最大尝试次数（默认最多3）、初始500ms指数退避+full jitter、退避上限5秒、总时间预算90秒；识别Retry-After，超预算停止，线程中断立即结束。不是所有HTTP400都重试，需明确特定可恢复错误；合法Schema冲突不应被网络重试掩盖。

源码：[OpenAiCompatibleClient.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/client/OpenAiCompatibleClient.java)。这个优化是运行传输可靠性设计，不能把retry后成功率从一次特定测试推广为整体真实模型可靠性。

## 三、模型调用成本控制：轻量模型、规则捷径、受控降级

V1时ContextRewrite、Routing、ConstraintExtractor、ToolPlanner可能分别让模型理解同一句话。8月24日Rewrite独立走qwen-flash、主模型仍deepseek-v4-flash；Run10在12条conversation轨迹平均9698ms，对照此前Run9的12292ms，但期间模型环境与工具命中亦变，必要工具覆盖从7/8降至6/8，不能把平均下降21.1%当作无质量损失的模型替换收益。

8月28日通过规则优先、上下文完整性判断与条件Routing减少不必要的双模型调用；41条轨迹单次A/B完整通过18/41→21/41，模型请求50→49，输入Token3809→3657，输出5137→4774，**位置正确率41/41→40/41、平均耗时16.57→16.71s**。这属于有回退的方向性结果，不是已统计显著的加速证明。

8月30日对叙事生成和答案润色做8+8样本的qwen-flash/deepseek对照；轻量生成在受限表达中减少Token与部分等待，同时其安全措辞在这组样本里更合约。此时仍为V1的narrative/polish架构。9月14日V2转用封闭事实渲染及有界Action后，不应将旧润色器的历史优化当成当前V2每轮仍必调用的步骤。

## 四、状态变更记录与过程事件不能混用

早期系统只输出零散AI日志，难以证明到底是模型、策略还是工具造成失败。V40将AI运行领域表统一为tbl_ai_*，区分：
- Working Memory：当前版本化业务事实，(chat_id,version)为唯一并发保护；
- Runtime Event：用户输入、模型解释/改写、工具计划和返回、最终回复等**历史执行事实**；
- Evaluation Run/CaseResult：一次实验的结果，是另外一类记录。

8月29日事件入口进一步分为：
- **Durable状态及交互事实**：STATE_REDUCED与Memory版本同事务；USER_INPUT等需要可靠记载的事件走持久化；TOOL_CALL写入后才真正执行工具，避免“工具执行了但调用事件完全没有记录”；TOOL_RESULT写失败不会盲目再次调用远端工具，可能形成traceIncomplete。
- **Best-effort过程观测**：REWRITE、ROUTE、POLICY_DECISION等可以缓冲异步批量落库，失败不能冒充业务状态失败；可用INSERT IGNORE降低重复记录阻塞整批。

这里没有引入Kafka/Outbox/CDC等独立消息设施，不能写“实现了严格Exactly-Once事件流”。Tool timeout也只证明Agent侧超时，不代表远端真实执行一定中止。

[ConversationEventService](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/ConversationEventService.java)、[V40迁移](https://github.com/huwuhu6/dp-plus/blob/main/src/main/resources/db/migration/V40__ai_runtime_table_prefix_and_event_model.sql)。

## 五、客户端重复提交与会话并发是两个不同问题

请求A、B并发修改同一聊天但彼此代表不同意图时，需要OCC：每次基于expectedVersion提交，数据库(chat_id,version)唯一键防两次拿同一版本写入。

而一个请求因为网络重试被执行两次时，需要幂等：tbl_ai_idempotency_record依据userId+chatId+scope+idempotencyKey识别同一个命令；requestHash一致且此前SUCCEEDED可返回旧结果，hash不同拒绝；PROCESSING请求也不能当已经成功。V53首版没有chat作用域，随后V54补入chatId，防同一用户在不同chat复用相同Key时错误重放。

V1工具返回慢时，如果读取时Memory为V20、工具结束时已到V21，直接应用旧ToolStateDelta可能覆盖新焦点；历史做法拒绝旧结果。V2分别为PRE与POST提供受限重试：PRE重新Grounding，POST在因果输入未变时复用观察，否则有限replan/re-execute，不能当作“冲突后随便把旧patch合入最新版”。

8月29日定向测试覆盖版本冲突、重复Key、跨chat作用域、缓存Redis原子追加；**没有真实双端并发lost-update/conflict-rate/P95对照试验**，所以不能宣称并发争用下吞吐提升。

## 六、为什么SSE本身也是独立工程主线

同步聊天可能一次等完整模型、地图和工具执行后才得到回复。V1新增POST /ai/chat/messages/stream，使用SseEmitter及虚拟线程，不建立第二套聊天事实状态；SSE事件包括status、text_delta、ui_component、suggested_chips、complete。商户卡片和快捷追问来自后端已确认商户字段，而非模型临时编造。

早期main模型仍为同步请求，status可先下发，最终文本再分片发送，因此不能把“采用SSE”说成一定有真正的模型Token流。**当前main的ChatStreamService已存在模型增量输出路径**（modelTextStreamed标记和sendModelTextDelta），不能继续把2026-08-25的历史限制当成当前完整实现；不同请求分支是否实时产出模型Token，应以实际聊天Service接线和浏览器实测为准。

“complete发送了”只代表服务端尝试发送，不能证明客户端一定收到并落UI。服务端事件的持久化先于某些SSE帧，客户端断连后的确切业务重放仍需要幂等键/可靠重取，而不是无条件再执行完整工具。

历史SSE冒烟：普通对话收到status→text_delta→complete；推荐收到status→text_delta→ui_component→suggested_chips→complete，结构化卡片有真实shopId与价格。JMeter低负载8条AI请求0%错误、平均约4.34s、P95约5.02s：规模很小，非并发容量Benchmark、非V2主链性能。

[ChatStreamService.java](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/ChatStreamService.java)。

## 七、长时间多轮评测为何要异步接收runId

旧版同步POST /ai/evaluations/conversation-runs在Nginx默认60秒超时下，浏览器会收到504，但后端可能实际继续跑完并写入数据库。用户看到的是“请求失败”，而实际实验已经存在，重复点击会生成重复Run或误导指标。

8月25日评测改为：同步创建RUNNING记录，立刻返回runId；在虚拟线程执行全轨迹，并恢复提交者UserHolder，结束后写回聚合指标；客户端GET查询进度与最终结果。运行中断通过显式ABORT标记，不静默将永久RUNNING当作已完成。

这条异步策略改善的是长评测提交/查询契约，不意味着真实聊天本身可以离线无限后台执行；也没有自动复原任意中断实验的能力。

## 八、当前已证实的工程边界

| 机制 | 当时明确解决的风险 | 未证明/仍存在的风险 |
|---|---|---|
| 超时配置与模型传输重试 | 不能把未生效超时当保护；临时服务异常可有界重试 | 不能对不可恢复语义错误反复重试；无长期成功率实验 |
| 规则优先Routing | 不必每个确定性动作都经模型 | 单次A/B仍有地点退化、无统计显著 |
| Runtime Event分层 | 业务状态/执行过程可分别审计 | best-effort可漏观测；无严格跨系统Exactly-Once |
| 幂等与OCC | 防同一命令重复提交、基于旧版本覆盖 | 请求无Idempotency-Key则无重试幂等；无实测高并发吞吐 |
| SSE | 同步/流式共用chat状态与结构化卡片 | 客户端ACK、断连重放、真实TTFT需单独评测 |
| 异步评测 | 避免长Run HTTP 504掩盖后端完成 | 不代表任务取消/worker中断自动恢复已实现 |

> 【核心提炼】可靠性首先要划清不可重复的业务动作和可重试的传输动作；其次划清已提交的状态事实和仅供诊断的过程事件；最后划清服务端已执行与客户端已收到。把“有重试”“有SSE”“有日志”直接写成高可靠是不成立的。
