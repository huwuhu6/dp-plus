# 评测体系与真实结果演进：如何从单轮得分走到多轮轨迹、语义契约与V2验收

> **先说明边界**：本文补录的是Git仓库开发记录、评测文档已记载的**历史运行结果**，并非此次新增执行的Run。不同评测Service、datasetVersion、模型、环境、数据快照和断言版本下的“通过率”不可直接相减。历史Run号要连同**所属评测集**一起识别。截止main 821422d，没有可严格复原、控制全部变量的Agent V1→V2整体准确率提升实验。  
> **本篇与其他专题的区别**：00—04讲功能为什么演进，本篇解释如何设计、运行、审计对应评测，哪些数字支持什么结论。已知测试例和断言保持原样。

## 1. 最早为什么不能只凭“回答看起来不错”判断Agent好坏

一条推荐“找三家福州日料”至少包含五个可以独立出错的动作：模型识别预算与地点、Java执行硬过滤、向量对合法商户排序、结果的事实与证据引用、无候选时的策略处理。只检查最终话术会遗漏某些严重问题：返回的店其实超预算；分数很高的店没有评价证据；用户没给位置却偷偷用了另一城市GPS；主搜索没找到店便自行放宽硬约束。

8月15日建立持久化的AiEvaluationCase / Run / CaseResult，评测走**真实ConsumptionDecisionService**，而非临时模拟另写一套搜索逻辑。保存用户查询、人工目标商户、状态、候选、硬条件违反、事实一致、证据覆盖、模型次数、错误和版本。后来V8保存模型/策略/数据集版本，V10记录平均/P95和模型提取耗时，V11/12记录模型失败并对历史可证明的计数做安全回填。

最先踩到的坑是分母：15条混合测试里5条本来就应CLARIFYING或WAITING_RELAXATION，它们没有排名候选，不能作为MRR=0样本。原始聚合误得MRR 0.6333、证据覆盖0.5787；后来单独维护rankingEvaluatedCount，排序只对**有GT商户、实际需要排序**的用例算，状态机仍计入状态/约束分母。这不是模型性能优化，而是**测量口径修复**。

另一个坑：GT不能只硬编码唯一商户。若用户的约束同时支持三家店，标注单个ID会把合法的不同排序误判失败。因此允许多个可接受目标，同时保存逐字段的constraint_mismatch，避免“错了”却不知道预算、位置还是菜系错。

证据：[开发记录8月15日](https://github.com/huwuhu6/dp-plus/blob/main/doc/AI消费决策Agent开发记录.md)、[AiEvaluationService](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/AiEvaluationService.java)。

## 2. 8月15日：第一次有对照，也第一次知道质量不能代表时延

### 2.1 Run5→6：同一15条seed-v1的约束命中

历史记录：同模型deepseek-v4-flash、同15条seed-v1、检索策略v1→v2，约束命中**14/15→15/15**（增加一条），差6.67个百分点。核心变化是将“女朋友/男朋友/情侣”等表达确定性补足为约会场景；其他报告指标未下降。这是该15题集合里的实际单变量方向性证据，不是任意自然语言的模型约束准确率。

### 2.2 Run7→8：修复超时与降级，但P95变差

| 指标 | Run7 | Run8 |
|---|---:|---:|
| 模型调用成功 | 8/15 | 15/15 |
| 运行平均总耗时 | 4584ms | 4040ms |
| P95总耗时 | 5915ms | 6968ms |

Run7暴露两条不同根因：失败回退的规则只认公里，不认“100米”；配置写了20秒超时却未真正配置到底层HTTP Client。修复后模型成功数提高、平均耗时变短，但尾延迟反而变长。这说明不能“平均更快”就声称性能全面优化。

Run7与Run8不是纯粹的同逻辑A/B，包含超时与降级处理修改；数据应按**真实回归观察**而非可信度很高的性能因果实验使用。

### 2.3 Run10/11与Run13/14：把“暂停”测成完整交互

V13把两条澄清/放宽用例扩成两轮：缺位置后提供坐标、严格100m零结果后用户授权扩大搜索。Run10（seed-v2，15条，其中两条实际续聊）状态与约束15/15，多轮两条均完成，平均3680ms、P95 5178ms。Run11同15题再跑，状态约束15/15，平均4689ms、P95 **16724ms**，证明正确性稳定与时延长尾不等价。

同一阶段固定的最终历史基线：

| Run | 评测集 | 状态/约束 | 续聊 | 排序/证据与硬条件 | 时延 |
|---|---|---|---|---|---|
| 13 | seed-v2，15条 | 15/15、15/15 | 2/2 | Recall@K=1、MRR=1、证据覆盖=1、硬条件违反0、事实15/15 | 均3958ms，P95 8262ms |
| 14 | holdout-v1，4条 | 4/4、4/4 | 1/1 | 同集合内上述指标均满分、违反0、事实4/4 | 均4020ms，P95 4476ms |

**边界**：这里的Run13/14属于最早的单轮+续聊评测，不是后续另一套conversation-v1的Run #13/14；4条Holdout尤其不能推广为线上正确率。历史v1/v2数据集切换以后，不允许把Run8与Run10时延直接算“优化”。

## 3. 8月24—26日：为什么评测必须变成真实多轮轨迹

单轮预测预算100正确，不意味着第二轮“预算不限”、第三轮“第二家怎么样”会正确保存前后状态。于是出现conversation评测Service：
- 每个Case具有多条user turns；每轮执行正式ChatOrchestrationService聊天链路；
- 采集路由、上下文改写、实际工具名称及参数、最终状态、位置/商户身份、候选批次与Working Memory断言；
- Case完整通过必须满足**该Case声明的全部断言**，不是模型API返回200或最后一句话通顺。

**真实失败：** 早期“第二家怎么样”改写器准确绑定第二家，但评测固定预期“筑地日本料理”，而新的排序顺序把第二家换成另一店，造成0/1的误报。后来改成candidateOrdinal=2，从上一轮实际推荐快照动态查第二家姓名再断言改写。实现正确的测试不能依赖会改变的候选顺序。

几个可独立确认的历史回放：
- Run9（conversation-v1，12轨迹）：条件细化保留预算200与3km、川菜→粤菜；本地无店导致WAITING_RELAXATION，并非虚假完成。
- Run14（同阶段12轨迹）：必要工具断言12/12，旧Run12为10/12；但同时改了其他逻辑，不能全部归因于Reducer。
- Run15（12轨迹）：将确实无候选时WAITING_RELAXATION设为合法终态，路由、工具、本地性、商户、最终状态均12/12；这属于修正错误预期后得到的结果，不能全部算产品能力提升。
- Run22（conversation-v1，14轨迹）：路由、工具断言、地点、最终状态均14/14，必要工具覆盖10/10，真实双事实“评价+优惠券”分别执行search_shop_evidence和query_shop_vouchers；平均整轨迹11707ms。
- Run25（conversation-v1，15轨迹）：路由/工具/位置/状态等均15/15，必要工具10/10，平均11636ms。新增默认3km→5km的结果策略属于系统默认半径，不能擅自放宽用户明确半径。
- Run28（conversation-v1，15轨迹）：修复高德MCP前置配置后路由/工具/位置/商户/最终状态15/15、必要工具10/10，均12129ms。
- Run35（V40之后的conversation-v1，15轨迹）：最终状态和关键路由15/15、必要工具9/10、均11125ms；一条“第一家那个日本料理”发生序号与店品类冲突，工具覆盖未全过。
- Run40（conversation-robustness-v1，5轨迹）：关键路由、地点、最终状态、Memory与错误恢复均5/5，均15224ms、P95 20886ms。后续并不代表所有鲁棒问题永久消失。

这些“满分”来自当时小集合及当时的断言体系，不应写作“V1多轮能力已100%”。

## 4. 8月27日：开发集、留出集、鲁棒集为何要分开

评测逐渐从“模型能否产生答案”转向更像真实回归的三组：
- conversation-v1主集：典型用户流程；
- conversation-holdout-v1：未用于当前调优的表达；
- conversation-robustness-v1：闲聊打断、跨城、退出恢复、状态负例等。

Run55—57是真实deepseek-v4-flash、MySQL/Redis/Milvus与持久Memory回放，41条轨迹。各Run全部Case pass需**所有已配置断言都通过**：

| Run | 集合 | 完整通过 | 路由 | 工具匹配/覆盖 | P95整轨迹 |
|---|---|---:|---:|---:|---:|
| #55 | 主集19条 | 15/19 | 17/19 | 18/19、10/11 | 33885ms |
| #56 | 留出16条 | 12/16 | 15/16 | 15/16、5/6 | 26718ms |
| #57 | 鲁棒6条 | 1/6 | 5/6 | 6/6、1/1 | 24763ms |

28/41只是这41条已配置轨迹整体“所有断言通过”的比例；当时实际模型调用49/49成功，位置与最终商户41/41，替代推荐8/8。鲁棒性1/6的重要根因之一是**商户世界变了，旧测试仍强制要求无候选和WAITING_RELAXATION**：真实数据库已经新增商户，成功推荐后Working Memory当然不是空。还有真实误路由、工具类型与期望不一致的问题。不能把旧断言过时和真实产品缺陷混为一类。

### 4.1 Milvus白名单下推之后的配对观察

#58/#59/#60分别对应上述同一主/留出/鲁棒集：
- 主集15/19→15/19，完整通过不变，均轨迹耗时增加409ms；
- 留出12/16→12/16，完整通过不变，平均减少646ms；
- 鲁棒1/6→1/6，工具匹配6/6→5/6，平均减少947ms。
- 实际日志中，合规3家只返回21个向量文档、合规12家返回63个；测试验证请求向Milvus携带allowed shopId filter，未出现Filter解析异常。

这些三组都使用真实大模型、数据和业务链路；模型工具路由本身可能波动，不能把轨迹时延波动视为ANN优化幅度。这组验证支持**白名单下推已被使用、主/留出集合质量无回退**。

## 6. 9月初：评测用例从数据库迁到Git可审查数据集

历史Case原来散在V23—V51大量Flyway插入/更新脚本中：想查一个用户用例为什么改变，需要追多次迁移；不同开发环境未必加载相同版本。9月5日用Git版本化JSONL维护 src/main/resources/eval/datasets/{datasetVersion}.jsonl，支持可审查diff与冻结数据集；运行结果仍保存在数据库，不把“题目定义”与“某次评测输出”混淆。

评测逐渐增加候选重排断言、最终Memory字段与推荐批次、工具事实匹配。过渡期间规则/评分器也变化，历史Run只能按当时版本解释，不能拿新断言倒灌旧Run结论。

## 8. 10月13—15日：为什么出现正式Main + Semantic Main + 受控业务验收

### 8.1 统一主成绩

| 统计 | V2 Main | Semantic Main |
|---|---|---|
| 数据集 | conversation-v2-main-v2 | conversation-v2-semantic-main-v1 |
| 正式Run | 201 | 202 |
| Case / Turns | 24 / 48 | 10 / 20 |
| 实际Case Pass | 24/24 | 8/10 |
| 模型成功/失败逐轮trace | 53/0 | 23/0 |
| 运行状态 | COMPLETED | COMPLETED_WITH_ERRORS |

同DeepSeek fixed0731、temperature0.1、默认模型单调用超时20s。报告没有可严格复核的两Run E2E平均/P95，**不补造耗时**。Run/Case层模型次数聚合为0是旧decisionSession计量路径漏V2，不能覆盖逐轮trace证据。

已确认Main 24/24的业务盲区：“没有藏式火锅就烧烤”被requiresCuisineCoverage要求主菜系包含备用烧烤，REPAIR写成错误OR，断言仍过；Semantic对应场景发生互斥字段语义失败。另一个SEM_CLEAR中模型无依据地产生人数、把预算100错抽到distance；来源校验拒绝并零提交。**模型FIRST可能正确，而确定性验证代码错**；评测不仅要检查格式，还要检查状态作用域与真实执行路径。

### 8.2 16场景/93项冻结业务验收

规范16场景、34条原话、53 MUST + 40 MUST NOT =93项。阶段收尾于SHA 27c2599：Maven530通过、8跳过。实际十场景TEST_ONLY首轮事实受控、真实后续用户语义十场景运行：4/10完整通过，S08/C03明确失败，S04/S09/C06/C15未完整验收。全部93项中44满足、3不满足、46未验证。**10/10“受控前提已就绪”不等于10/10业务通过，更不等于真实首轮模型通过**。

S02、S06、C23有同原话、同Fixture、同0731模型60s的局部修复前后运行：
- S02：GENERAL拒答问价→PRICE绑定商户22、真实受控价格40元及忌辣状态；
- S06：DETAIL漏掉无骨属性→PRODUCT绑定22并明确商品未知，不把未知当没有；
- C23：已执行同店选择但回复漏选店→事实+本轮实际选中两者一起回复。
修复前27cb6c93，后f04f94ea。它们只能证明三个**局部行为目标**，不能与201/202直接拼成整体提升。

## 10. 总结：评测体系本身也经历了架构演进

**从最初**“一条问句→返回店铺”的单轮质量评分，
**到后来**“同一chat每轮的路由、状态、工具、候选、异常恢复”的trajectory验证，
**再到V2**“强类型语义契约+执行观察+业务MUST/MUST NOT+冻结数据集+有限真实模型对照”。

伴随演进，真正影响结论可信度的是：GT是否过拟合具体商户、哪些样本应该计入分母、主集和Holdout是否隔离、评测器自身是否存在断言盲区、哪些运行具有完全相同的环境、哪个数字仅证明受控Fixture、哪个数字反映真实数据库和地图依赖。

> 【核心提炼】Agent评测不是只看Pass Rate，更关键的是知道“这个Pass究竟验证了哪个业务事实”，并能把模型错误、确定性代码错误、数据覆盖缺口、评分器错误和外部依赖失败明确分开。
