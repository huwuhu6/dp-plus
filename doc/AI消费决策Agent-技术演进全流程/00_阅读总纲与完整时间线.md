## 1. 业务到底是什么

假设用户在餐饮消费场景里连续提出以下需求：

~~~text
第1轮：在福州找人均100以内的火锅，最好离我近一点。
第2轮：第一家太贵了，第二家排队吗？
第3轮：那还是看看杭州日料吧，预算300。
第4轮：还是最开始福州火锅，不过预算80以内。
第5轮：如果3公里没有藏式火锅，就改找烧烤。
~~~

单轮推荐可以把输入抽成菜系、预算和位置，再去数据库找店；真正难的是第2—5轮：第二家属于哪一批？“太贵”只是价格反馈还是预算修改？杭州方案出现后，福州方案去哪了？回到福州时能否恢复旧条件而不捎带杭州预算？“如果没有X就Y”中的Y能否在条件发生前写入长期状态？

这几个问题背后有一条共同主线：**大模型适合理解开放语言，但程序执行必须建立在唯一、可追溯、有权修改、能确定提交的业务事实之上。** Agent不能每轮都让模型重新猜“当前世界是什么”，也不能让任何一条工具结果随意更新世界。

系统边界：Java/Spring Boot承载聊天、模型、业务状态及编排；MySQL保存商户、画像、评论投影、会话状态、运行事件和评测；Redis保存聊天缓存等；Milvus提供商户画像与评价文档的语义分数；地图/POI服务在可信条件下确定搜索锚点。不同依赖不可互相代替——Milvus没有权力让不满足人均上限的店入选，模型也没有权力凭空断定某店有无骨鸡肉。

### 2.1 2026-08-14—16：从单轮推荐进入受控多轮

早期：模型输出结构化筛选字段，Java执行过滤和结果组织。真实问题：模型没有天然看到HTTP请求里单独携带的设备坐标；请求缺位置时如果直接执行，可能把无地点需求解释成随意的附近搜索；硬过滤无店时为了“给个结果”放宽条件会违背原话。因此出现位置澄清、严格零结果、放宽授权等状态。并开始区分真实商户事实与模型最终语言表达：模型可解释推荐原因，不能修改价格、评价或商户身份。

此时系统能够解决有限多轮追问，但信息分散在聊天历史、会话槽位、临时Pipeline、候选列表和决策会话执行快照中，尚不存在统一的长期业务记忆。

证据：[开发记录：单轮到状态机](https://github.com/huwuhu6/dp-plus/blob/main/doc/AI消费决策Agent开发记录.md)；[JDK21/SpringBoot3及混合检索底座](https://github.com/huwuhu6/dp-plus/blob/main/doc/AI消费决策Agent开发记录.md)。

### 2.2 2026-08-16—24：位置、聊天历史与候选引用拼出第一套“会话状态”

用户说“第二家怎么样”，模型不应该生成一个shopId。系统需要记录有序候选、焦点商户和地点，再依据真实的推荐结果识别“第二家”。位置槽位和候选信息初期仍分散：会话位置和某一次决策的执行上下文不属于同一张表。跨轮条件“预算改为80”还无法可靠继承“之前的福州和火锅”。

当时固定Pipeline的方向是 Bootstrap → Context Rewrite → Intent Routing → Criteria Reduction → Policy Guard → Execution。这个顺序后来在V1真实使用，但不是今天V2的主链。早期Rewrite尤其有帮助——信息只能从聊天文本里找；后来它与结构化指代、路由、抽取之间职责开始重叠，复合句容易发生语义损失。

### 2.3 2026-08-24：Working Memory不是聊天摘要

引入 ConversationWorkingMemory 和 ConversationCriteriaMerger：旧状态为基线，本轮只表达变更；未提及的保留、明确改值的替换、明确取消的清除。历史例子：“附近人均200以内的川菜”→“不要辣的，换粤菜”。预算200、半径3km继续有效，菜系改为粤菜；因当时数据覆盖不足，最终可能进入等待放宽状态，而非不合条件地凑店。Run9记录了这条真实行为，不能将“请求被正确解析”当成“成功推荐到店”。

随后发现更新菜系却继续沿用旧的川菜候选。State Reducer根据合并结果级联失效候选与焦点，强调：**约束已经变化，旧的派生结果就不能继续作为当前结果；但真正的历史事实可保留。**

证据：[32daa32f](https://github.com/huwuhu6/dp-plus/commit/32daa32f)、[39ecba3f](https://github.com/huwuhu6/dp-plus/commit/39ecba3f)、[042546aa](https://github.com/huwuhu6/dp-plus/commit/042546aa)。

### 2.4 2026-08-26—29：让状态变成“版本”和可追踪的“事件”

再往前一步：两个窗口同时修改同一chat会发生旧快照覆盖。于是使用 tbl_ai_working_memory 按(chat_id,version)追加完整JSON快照；expectedVersion与唯一键负责OCC；与状态变化关联的Event同事务提交。其他Rewrite/Route/Tool事件是执行审计，不应每写一条Event就额外生成业务Memory版本。这是Memory（此刻事实）与Runtime Event（发生过什么）分离。

8月29日前后加入更多操作的请求幂等记录，解决客户端重复提交与同一请求重放；但**幂等不等于OCC**：幂等针对同一个请求键防重复执行，OCC针对同一会话不同操作的并发写入资格。两个机制可以同时存在。

证据：[e526ea29](https://github.com/huwuhu6/dp-plus/commit/e526ea29)、[V40表迁移](https://github.com/huwuhu6/dp-plus/blob/main/src/main/resources/db/migration/V40__ai_runtime_table_prefix_and_event_model.sql)、[IdempotencyService](https://github.com/huwuhu6/dp-plus/blob/main/src/main/java/com/hmdp/ai/service/IdempotencyService.java)。

### 2.5 2026-09-03—07：状态语义的缺口不断被真实对话暴露

典型失败一：“看看有没有别的吃的”本来是放弃沙县旧菜系，但稀疏Delta的空值可能表示“没提及”，导致旧菜系继续继承。新增clearedFields、removedPreferences并形成显式清除操作。

典型失败二：“第二家太贵了”。不仅要识别相对预算意图，还要先找到哪个商户作为价格锚点；将“更便宜”变成明确、可执行的预算，且在没有结果时不能反过来给“提高预算”的放宽选项。V1曾使用基于锚点的比例收紧与锁定维度；V2后来将相对意图保持为独立语义项，不冒充用户原始绝对值。

典型失败三：在福州火锅A、杭州日料B之间切换，Flat State只会覆盖。引入Task Scope：每套消费方案独立保存条件和推荐批次；历史Task保留，activeTaskId切换。第一版却仍在后续Reducer重新从数据库读到旧快照，覆盖了内存里刚刚完成的切换；修复为同轮权威内存后，Task定向子集2/4→4/4，**当时完整Run89仍仅7/24**。Task模型对了≠调用链一定用对了。

典型失败四：“福州大学”和“重庆鸡公煲”出现地名，却不代表用户明确指定行政城市。Prompt优化在局部评测有所帮助，但还需要Java/地理服务确认实体身份；位置串扰可直接造成错误的硬过滤。

证据：[81d8ace4](https://github.com/huwuhu6/dp-plus/commit/81d8ace4)、[77846543](https://github.com/huwuhu6/dp-plus/commit/77846543)、[472da9da](https://github.com/huwuhu6/dp-plus/commit/472da9da)、[da5b06bd](https://github.com/huwuhu6/dp-plus/commit/da5b06bd)、[开发记录](https://github.com/huwuhu6/dp-plus/blob/main/doc/AI消费决策Agent开发记录.md)。

### 2.6 2026-09-14：V2为什么不是“继续在V1上加if”

旧版的Context Rewrite、Routing、Constraint Reduction、实体引用、任务恢复和策略判断分别理解同一句话。复合句里可能既有历史反馈、又新开任务、又查某家店价格，系统必须回答：“反馈落给旧Task还是新Task？”“历史指代可以读旧批次，但是否允许恢复整个旧任务？”“模型提到了烧烤，是主条件还是主搜索EMPTY后的备用条件？”

V2采取独立的强类型领域核：TurnSemantics表达本轮语义，RequirementChange表达确定变化/相对偏好/条件变化，Grounding绑定商户和Task身份，PreExecutionReducer只提交不依赖工具结果的用户事实，PlanningSnapshot冻结执行依据，Compiler编译有界DAG，Executor产出观察和DomainEffect，Verifier检查硬约束，PostExecutionReducer根据效果修改状态。PRE与POST分别通过OCC提交。

这里有两个不同的Git节点：
- [fdf016ca](https://github.com/huwuhu6/dp-plus/commit/fdf016ca)：先建立独立V2领域核，**V1主聊天入口未切换**。
- [0c48ab0b](https://github.com/huwuhu6/dp-plus/commit/0c48ab0b)：将主入口切到V2ChatOrchestrator；后续提交物理清除旧主链语义节点（旧文件/兼容基础设施的存在不代表仍是主链）。

V2的语义核心与约束生命周期详见02、04篇。不能只用“教科书式架构重构”四字跳过数据流或假定阶段性验证已证明所有复合意图。

### 2.7 2026-10-13—15：围绕真实模型语义和评测契约反复定位

这阶段主要不是新增一条大Pipeline，而是检查最新V2对真实自然语言、历史商户引用、事实工具、位置、菜单和条件分支是否真的闭合。包括：历史事实查询不能擅自恢复历史Task；模型FIRST遗漏复合菜系后尝试定向字段修复；字段来源不可靠时零提交；POI唯一完整名称被相关建筑遮蔽；首轮搜索条件无供给时必须返回诚实零结果。

10月15日统一评测：
- V2 Main：Run201，24 Case、48轮，现有断言24/24；
- 独立V2 Semantic：Run202，10 Case、20轮，8/10；
- 阶段收尾：16场景/93项要求中，受控运行10场景，4/10完整通过；530 passed、8 skipped是Maven代码回归，不是模型或业务通过率。

**关键反例**：“如果3公里没有藏式火锅，就改找烧烤”。模型FIRST正确识别主菜系与备用菜系，但requiresCuisineCoverage连同整句requestedCategories把备用烧烤误要求进入主菜系。Main修复成错误OR仍因断言盲区24/24；Semantic形成单选与OR冲突并失败。错不在FIRST，出在后处理校验。另一个独立代码边界是备用搜索返回EMPTY（非技术失败）时，执行组仍可能发出ConditionalCriteriaApplied，POST提交备用约束；这一项有代码链审计，**没有本次独立运行复现**。

## 4. 最后采用的方案是什么：只介绍结构不代替细节

当前主入口在 V2ChatOrchestrator。关键状态归属是：
- **ConversationWorkingMemory**：按chat保存业务状态集合，包括当前Task、任务列表、设备位置与对话焦点。不是最近八条聊天文本，也不是Prompt。
- **DecisionTaskState**：一套可回来的用餐安排，包含规范DiningCriteria、相对偏好、排除/锁定集合、历史推荐批次、Task生命周期、搜索锚点。不是一个HTTP请求，也不是一个线程。
- **TurnSemantics**：一次用户输入提取出的任务命令、条件变化、实体反馈、请求、关系、实体引用。该对象本身不是已提交的长期状态。
- **PlanningSnapshot**：PRE OCC成功后冻结的计划依据；执行期不应再读一份不断变化的WorkingMemory替代它。
- **ExecutionPlan**：带有依赖和守卫条件的有界静态执行组；目前Compare/Adaptive部分场景明确不支持。
- **VerificationReport**：校验候选身份、重复、排除集、预算/距离/菜系硬条件和证据缺口，不会直接替换用户要求。
- **WorkingMemoryVersionService**：写入资格与事务性版本保存；V2 PRE/POST采用不同的冲突处理语义。

~~~mermaid
flowchart TD
    U[用户本轮原话] --> S[SemanticInterpreter: 本轮结构化语义]
    S --> M[读取最新Working Memory]
    M --> T[Task归属与Grounding]
    T --> PR[PRE Reducer: 可立即确定的用户事实]
    PR --> C1[OCC提交PRE]
    C1 --> PS[冻结PlanningSnapshot]
    PS --> CP[Compiler: 静态计划或直接动作]
    CP --> EX[Executor: Search/Tool/DomainEffect]
    EX --> VE[Verifier: 硬条件/证据门]
    VE --> PO[POST Reducer: 执行后效果与推荐批次]
    PO --> C2[OCC提交POST]
    C2 --> R[Renderer形成用户回答]
~~~

## 5. 证据与指标使用规则

**所有数字先写分母、测试环境和被验证能力，后写结果。** 早期的Task Scope定向2/4→4/4是局部失败簇；历史检索35条相同查询的Recall@3 0.7291→0.7614是语义分数消融；Run201和Run202是两套不同的正式评测集合；代码回归530 pass与受控自然语言4/10没有加总意义。
